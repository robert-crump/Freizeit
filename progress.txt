## 2026-07-25 — Issue #24: Permission opt-in flow for auto check-in

- Picked over #25/#26/#27 (all unblocked now that #23 is closed): this is the one
  that unblocks #28 (auto-detect proximity notification, the epic's core feature,
  currently `ready-for-human` pending this permission groundwork) — #25 is a
  docs-only amendment and #26/#27 are UI/ranking polish on top of already-shipped
  check-in, neither unblocks anything else.
- The issue text claims "there is no existing permission-request flow to extend,
  this is net-new" — false. `HomeScreen.kt`/`ExploreScreen.kt`/`CheckInScreen.kt`
  all already request `ACCESS_FINE/COARSE_LOCATION` unconditionally in a
  `LaunchedEffect(Unit)` on first composition, no rationale, no opt-in gate (Home
  is the start destination, so this fires at effectively first app launch).
  Deliberately left untouched — that's pre-existing, separate behavior for
  foreground GPS fixes used by suggestion ranking, not this issue's scope. Made
  sure the new auto-check-in toggle's permission chain is independently gated
  (only ever launched from the Settings toggle's `onCheckedChange`) rather than
  reusing/short-circuiting on the fact that Home may have already gotten
  foreground location granted for free.
- `SettingsRepository`: new `autoCheckInEnabled: Flow<Boolean>` /
  `setAutoCheckInEnabled()`, a second `booleanPreferencesKey` alongside
  `suggestionRadiusKm`'s existing `intPreferencesKey`, same DataStore file, same
  upsert-flow shape. Default `false` (off by default, per the issue).
- New `util/AutoCheckInPermissions.kt`: thin `ContextCompat.checkSelfPermission`
  wrappers for the three permissions, mirroring `LocationHelper.hasPermission`'s
  existing style (no test file — same as `LocationHelper`, which also has none).
  Background-location/notifications read as already-granted below API 29/33
  respectively, since those permissions don't exist as a runtime concept there —
  keeps the Settings status rows from showing a permanent false "Denied" on
  older OS versions.
- `AndroidManifest.xml`: added `ACCESS_BACKGROUND_LOCATION` and
  `POST_NOTIFICATIONS` declarations (previously only fine/coarse foreground
  location existed).
- `SettingsScreen.kt`: new "Auto check-in" section, `Switch`-bound to the
  DataStore flag directly (single source of truth — the switch only ever shows
  on once the DataStore write actually happens at the end of a successful
  chain, never optimistically). Turning it off just writes `false` immediately,
  no permission dance needed. Turning it on shows an `AlertDialog` disclosure/
  rationale screen first (reused the `AlertDialog` pattern from Explore's
  existing `CustomNameDialog` — no `Dialog`/nav-route infrastructure needed,
  consistent with this app having no sub-screen nav pattern yet, confirmed by
  `FreizeitDestinationTest`'s hardcoded 4-route assertion). Confirming the
  dialog kicks off three chained `rememberLauncherForActivityResult` callbacks
  (foreground → background if SDK ≥29 → notifications if SDK ≥33, each
  triggering the next from its own result callback), ending in
  `onEnabledChange(true)` only if foreground location was actually granted — a
  full foreground denial stops the chain immediately and shows an inline denied
  hint instead of silently leaving a half-configured feature enabled.
  Per-permission Granted/Denied status rows (shown once the feature is enabled)
  refresh via a `DisposableEffect`/`LifecycleEventObserver` on `ON_RESUME`
  (mirroring `PlaceMiniMap.kt`'s existing mapView lifecycle pattern) so a manual
  grant/revoke via the system app-info screen is picked up on return to the app,
  not just after a launcher callback.
- Tests: 122 total (was 120 per #23's log — 118+3 VisitDao/CheckInRanking minus
  the trimmed #5 entry doesn't affect the count, just progress.txt itself), 26
  failed (unchanged) — the +2 are two new plain-JVM `SettingsRepositoryTest`
  cases (default-false, round-trip), confirmed via the per-class XML report
  that all 5 `SettingsRepositoryTest` cases are green and the 26 failures are
  the same 6 pre-existing Robolectric `UnsatisfiedLinkError` classes
  (PendingVisitDaoTest/PoiCustomNameDaoTest/VerdictDaoTest/VisitDaoTest/
  BackupRepositoryTest/PoiImportTest) documented since #10/#13/#15/#23 — no new
  class appears in the failing set.
- Not verified on device: the actual OS permission dialogs (esp. the Android
  10+ two-step background-location dance, which on real devices routes through
  a separate "Allow all the time" system settings screen rather than a second
  in-app dialog on some OEM skins) and the disclosure `AlertDialog` itself are
  unexercised beyond compiling/unit-testing the DataStore and chain-sequencing
  logic — needs a real run on Robert's phone, particularly to confirm the
  chain's sequencing survives Android's own background-location system UI
  detour rather than assuming a plain permission-dialog round trip throughout.

## 2026-07-24 — Issue #23: Manual check-in for nearby POIs

- Picked over #24/#25/#27/#29 on purpose: this is the foundational slice —
  #26/#27 are directly blocked by it, and #28/#29 transitively depend on it —
  while #24 and #25 are unblocked but don't unblock anything else themselves.

  `MIGRATION_3_4`, well before this session) — favoriting is a `Verdict` row
  with `value == Verdict.VALUE_FAVORITE` now. Read the DB layer before
  writing anything rather than trusting the issue's stale description.
- New `Visit` entity (`data/entity/Visit.kt`): auto-generated `id` (it's an
  append-only log, not a singleton row like `PendingVisit`) plus the same
  denormalized snapshot fields (`placeId`, `visitedAt`, `source`,
  `snapshotName/Lat/Lon/Category`) `Verdict`/`PendingVisit` already use, for

  against the entity like every prior migration in this file.

  distance, capped at 500m") is a new pure top-level function,
  `rankNearbyForCheckIn()` in `CheckInViewModel.kt` — same convention as
  `filterAndSort`/`withinRadius`/`nearestFavoriteWithin`, so it's unit-testable
  without Robolectric. Favorites *beyond* 200m aren't excluded — they just
  lose top billing and fall into the ordinary distance-sorted group, which

  X") confirms it, following the same pattern as Settings' `ImportStatus`
  banner rather than introducing a Snackbar (no Snackbar exists anywhere in
  this codebase yet).
- Reused `CategoryDot`/`Poi.displayName()` from `ui/explore/PlaceDetailSheet.kt`
  (both already public) instead of duplicating them — the row layout mirrors
  `ExploreScreen`'s `PoiSuggestionRow` closely on purpose.

## 2026-07-24 — Issue #21: Filter suggestions by distance

- Design was worked out via a full /grill-me pass before writing any code
  (distance origin, no-location behavior, filter placement, empty-state
  precedence, settings persistence, UI control, commit timing, scope,
  test scope — all resolved with the user first). Implementation matched
  that design exactly; no surprises during coding.
- This is the app's first-ever persisted user setting — no DataStore or
  SharedPreferences existed anywhere in the codebase before this issue.
  Added `androidx.datastore:datastore-preferences:1.0.0` and a new
  `SettingsRepository` (`data/repository/SettingsRepository.kt`) wrapping
  a `Context.settingsDataStore` delegate declared in `AppContainer.kt`,
  following the existing lazy-property-per-repository DI pattern exactly.
  `suggestionRadiusKm` is a `Flow<Int>`, default 40, coerced to a minimum
  of 1 on both read and write (no upper cap, per the issue).
- `SuggestionEngine.withinRadius(pois, location, radiusMeters)`: a new
  pure function, deliberately kept separate from `evaluate()`'s existing
  closed-hours/bad-weather hard filters (rather than folded in) so
  `HomeViewModel` can tell "nothing is within range" apart from "in range
  but nothing currently fits" — the two need different empty-state copy.
  `location == null` (no GPS fix yet) skips the filter entirely rather
  than measuring against a guess — same principle as the existing
  Cologne-fallback weather-only default, but the fallback itself is
  *not* used for distance filtering (flagged as its own investigation,
  issue #22, since nobody could say why Cologne specifically without
  digging further).
- `HomeViewModel`: added `settingsRepository` as a 6th constructor param
  and a 5th flow in the existing 4-flow `uiState` combine (still within
  the stdlib direct-lambda overload limit, no arity workaround needed
  this time). New `HomeUiState.hasFavoritesWithinRadius` /`.radiusKm`
  fields; `hasFavoritesWithinRadius` is `true` whenever there are no
  favorites to judge in the first place or location is unknown, `false`
  only when real favorites exist but all fall outside the radius.
- `HomeScreen.kt`: new branch inserted between the existing `!hasFavorites`
  and `deck.isEmpty()` hints — `!hasFavoritesWithinRadius -> CenteredHint(
  "No suggestions within %d km.")`. Reused the existing `CenteredHint`
  composable verbatim (a plain non-swipeable `Text`), which satisfies the
  issue's "should not be swipeable" requirement for free — the swipe
  gesture code in `SwipeableSuggestionCard` is never reached from any of
  these hint branches.
- Settings UI: new "Suggestions" section in `SettingsScreen.kt`, a single
  `OutlinedTextField` (digits-only `onValueChange` filter, numeric
  keyboard). Commits to `SettingsViewModel.setSuggestionRadiusKm` only on
  blur (`Modifier.onFocusChanged`), not per keystroke, and reverts the
  displayed text to the last-committed value if left blank/non-numeric —
  first input-style control this screen has ever had (previously only
  buttons).
- Deliberately out of scope, per the design discussion: the radius only
  filters Home's suggestion deck, not Explore's favorites/map (issue
  title and body are both Home-specific); no "home address" concept was
  introduced — distance is measured from the same live/last-known device
  location `SuggestionEngine` already used for scoring.
- Tests: 111 total (was 104), 0 new failures — the pre-existing 23
  Robolectric `UnsatisfiedLinkError` failures (MapLibre native init
  triggered by any test touching `ApplicationProvider.getApplicationContext()`,
  documented since #15/#16) are untouched, same classes/count as before
  this issue. New: `SuggestionRadiusTest` (4 cases — in-range, exact

  `SettingsRepositoryTest` (3 cases — default, round-trip, non-positive

  repository tests hit.
- Not verified on device: the on-blur commit behavior of the new text

## 2026-07-15 — Issue #14: Widen POI extraction to shop/tourism/leisure_other/office/craft/historic

- Picked over #15/#16 since both are blocked transitively on this one (#15
  directly, #16 via #15) — this was the only unblocked ready-for-agent issue,
  and this machine has the Ride-Graph `.pbf` sources + `osmium` venv the
  issue's note flags as a hard requirement.
- `extract_pois.py`: split the old single `CATEGORIES` dict into
  `EXACT_CATEGORIES` (the original 5 — playground/park/cafe/restaurant/
  ice_cream, unchanged key=value matching, no name requirement) and a new
  `COARSE_CATEGORIES` (shop/tourism/leisure_other/office/craft/historic —
  matches any object carrying the given top-level OSM key regardless of
  value, but only when it also has a non-empty `name` tag). `categorize()`
  checks exact first, then coarse, so e.g. `leisure=playground` still
  resolves to "playground" and never falls into `leisure_other`
  (`_LEISURE_EXACT_VALUES` exclusion). The name requirement was in the
  issue's acceptance criteria, to keep the coarse keys from pulling in
  unnamed street furniture (benches, vacant shops, etc.) — confirmed
  necessary by the coverage report below.
  `filter_keys` for `osmium`'s `KeyFilter` widened to the union of both
  dicts' keys so the new categories actually get read from the .pbf stream.
- `README.md` updated: documents the exact-vs-coarse split, the name-tag
  rule and why it exists, and the expanded `categories` field in the output
  example.
- Ran via the Ride-Graph venv against the real full extracts (koeln-regbez,
  limburg, wallonia_french/german — not `precut/`). `data/pois.json`
  regenerated in place (git-ignored, not committed). Coverage report:
  playground 9635 (14.1% named), park 4466 (28.5%), cafe 3037 (94.7%),
  restaurant 10145 (97.6%), ice_cream 612 (96.4%) — all five unchanged in
  shape from before this issue, confirming the exact-match path wasn't
  touched. New categories, all 100% named by construction: shop 45772,
  tourism 16904, leisure_other 9004, office 11450, craft 3745, historic
  15955. 130725 POIs total (2749 cross-extract duplicates dropped), up from
  ~28k pre-#14.
- No test harness exists for this Python tool (none did before either) and
  no app/Kotlin code was touched, so no Gradle run — this issue is data/
  tooling-only. #15 (Room import/query) and #16 (map pin styling) are the
  ready-for-agent issues that consume this new data next.
