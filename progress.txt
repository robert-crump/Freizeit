## 2026-08-02 — Issue #44: Check-in history date-bucketed sections

- Spec was fully resolved via `/grill-me` before this pickup (bucket priority order, calendar-
  based vs rolling windows, locale week start, sticky inert headers, per-row timestamp format by
  section, empty-bucket hiding) — posted to #44, implemented directly from it with no further
  clarification needed.
- New pure function `bucketVisits` (`util/CheckInHistoryBuckets.kt`): groups a `List<Visit>` into
  `VisitSection(label, visits)` buckets — Today, This week, Last week, This month, Last month,
  then one "March 2026"-style bucket per older month — using `WeekFields.of(locale)` for the week
  start rather than a rolling 7-day window, so results genuinely change with device locale (US
  Sunday-start vs. UK/DE Monday-start). Relies on `visits` already being sorted newest-first (as
  `VisitDao.observeAll()` returns it) and on the bucket windows being non-overlapping,
  chronologically decreasing intervals: grouping in encounter order via a `LinkedHashMap` yields
  correctly-prioritized, already-deduped section order for free, no separate sort/priority-list
  step needed. Year rollover (a December visit bucketed while "now" is January) falls out of
  plain `LocalDate` month arithmetic (`minusMonths`, `YearMonth.from`) rather than needing
  special-cased logic — verified with a dedicated test rather than assumed.
- Per-row timestamp reformatted now that headers carry the date (`util/DateTimeFormat.kt`): new
  `formatVisitTimeOnly` (time only, e.g. "3:45 PM", for the Today section) and
  `formatVisitWeekdayAndTime` ("Tue, 3:45 PM", every other section) sit alongside the existing
  `formatVisitTimestamp` (full medium date+time) rather than replacing it — that one's still used
  by `CheckInDateTimeFlow.kt`'s confirmation screen, out of this issue's scope.
- `CheckInScreen.kt`: `LazyColumn`'s flat `items(state.visits)` replaced with a `sections.forEach`
  loop emitting one `stickyHeader` (new `SectionHeader` composable — inert `Surface`+`Text`, no
  click handling) per bucket followed by that bucket's `items(section.visits)`. `stickyHeader` is
  a direct `LazyListScope` member (not an extension needing its own import, unlike `items`) —
  initially imported it as one anyway and hit an "Unresolved reference" compile error before
  catching the mistake. `VisitRow` now takes the pre-formatted `timestampText` as a param instead
  of formatting `visit.visitedAt` itself, so the Composable doesn't need to know which section
  it's in beyond what the caller already decided. Headers are naturally invisible to
  `CheckInHistoryViewModel`'s existing select/delete/undo logic since that only ever operates on
  `Visit.id` values coming from `items`, never from the sections list — no ViewModel changes
  needed, as the issue predicted.
- Tests: new `CheckInHistoryBucketsTest.kt` (13 cases) covering today-vs-this-week priority, week/
  month boundaries, the week-start locale-variation case explicitly (same visit date buckets as
  "Last week" under `Locale.UK` but "This week" under `Locale.US`), locale-formatted month-year
  labels (`Locale.GERMANY` → "Mai 2026"), both year-rollover shapes (a December visit reads "Last
  month" in early January; a November visit two months back keeps "November 2026", not
  "November 2027"), empty-bucket omission, and section-order-follows-priority given already-
  sorted-desc input. 321 total tests, 0 failures. `compileDebugKotlin`/
  `compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean.
- Not verified on device: sticky-header pinning behavior and the header's opaque background
  actually occluding rows scrolling underneath it are Compose layout behavior no unit test
  exercises — worth a real scroll-through on Robert's phone, along with a visual check that the
  section header's `labelLarge`/`onSurfaceVariant` styling reads clearly against the list.

## 2026-08-01 — Issue #42: active-notification bugs

- Issue was a live bug report (unfavorited place still notified; two DWELL notifications arriving
  20min/1.5h after the fact) — root-caused via a `/grill-me` session before any code was touched
  (scope: both bugs in one pass; where the stale-favorite fix lives; whether to reconcile the live
  notification immediately and how, given no location fix is available on that path; which
  location API to use for the staleness check within `goAsync()`'s time budget; threshold/fail-
  open behavior; testing approach), posted to #42 as a comment, then implemented directly from
  that spec.
- Root cause 1 (stale favorite): `GeofenceSyncManager.register()` diffed registered geofences
  against current favorites and removed stale ones, but never touched
  `GeofenceStateRepository.dwellingPlaceIds`. An unfavorited-while-dwelling place has no geofence
  left to ever send an EXIT, so its id stayed "dwelling" forever — able to win
  `closestEligibleFavorite()` (and thus show a notification, or block a legitimate one) on any
  later, unrelated transition.
- Root cause 2 (late delivery): Play Services can delay a DWELL broadcast well past the requested
  `NOTIFICATION_RESPONSIVENESS_MILLIS` under Doze/standby batching — the event's own
  `triggeringLocation` reflects the real transition moment, not delivery time, so it can't detect
  this.
- New pure functions in `util/GeofenceNotificationSelection.kt` (tested in
  `GeofenceNotificationSelectionTest.kt`, 172 tests total / 0 failures):
  `reconcileDwellingOnUnregister(dwellingPlaceIds, idsToRemove, activeNotificationPlaceId)` — purges
  removed ids from dwelling state, flags whether the currently-shown notification (if any) needs
  cancelling; `isNotificationStale(currentLat/Lon, accuracyMeters, poiLat/Lon, radiusMeters)` —
  radius + accuracy-buffer distance check.
- `GeofenceStateRepository` gains `activeNotificationPlaceId` (nullable `stringPreferencesKey`):
  which favorite the single outstanding notification is for, so a favorites-change can tell
  whether it needs to cancel that specific notification.
- `GeofenceSyncManager.register()`: on each successful `removeGeofences()`, calls
  `reconcileDwellingState()` (new private helper) to purge + cancel-if-affected. No re-ranking is
  attempted here — no location fix available outside a geofence transition, so a still-dwelling
  favorite's notification is left alone for the next real transition to correct. `removeAll()` also
  clears `activeNotificationPlaceId` now, alongside the state it already cleared.
- `GeofenceBroadcastReceiver.refreshNotification()`: before showing a DWELL notification, checks
  `LocationHelper.lastKnownLocation()` (synchronous, cached — already used elsewhere in this
  codebase, no risk to `goAsync()`'s ~10s budget the way a fresh GPS fix would be) against the
  target favorite via `isNotificationStale`; suppresses (cancels) instead of showing if stale. No
  cached location → fails open (shows it) rather than silently dropping a legitimate notification.
  `showNotification`/`cancelNotification` helpers now wrap `GeofenceNotifications.show`/`cancel`
  to keep `activeNotificationPlaceId` in sync at every call site (`refreshNotification`,
  `handleCheckIn`, `ACTION_DISMISS`).
- `assembleDebug`/`testDebugUnitTest`: both clean, no new warnings.
- Not verified on device: the actual DWELL/EXIT timing and delivery-latency behavior this targets
  is inherently a real-device/real-Play-Services thing — needs confirmation on Robert's phone that
  (a) un-favoriting mid-dwell no longer resurfaces a notification for that place, and (b) a
  deliberately-delayed DWELL (e.g. airplane-mode trick) gets suppressed rather than shown.

## 2026-08-01 — Issue #40: update user location more frequently

- Issue was a stub (title + two-sentence body) — full design worked out via a `/grill-me` session
  before any code was touched (update model per screen, shared-vs-per-ViewModel location state,
  continuous-stream interval/priority, start/stop lifecycle scoping, manual refresh affordance,
  snapshot-vs-collect semantics for Home/Check-in, `GeofenceLocationMonitor` scope boundary —
  every branch resolved with the user first), posted to #40 as a comment, then implemented
  directly from that spec.
- Root cause: location was a plain one-shot `LocationManager.getLastKnownLocation()`
  (`util/LocationHelper.kt`), independently duplicated in `MapViewModel`/`HomeViewModel`/
  `CheckInViewModel` — no shared state, so the three screens could each show a different stale fix
  at the same moment; Map had no resume-based refresh at all.
- New `data/repository/LocationRepository.kt` (wired into `AppContainer` as a `by lazy` property,
  same pattern as `weatherRepository`/`geofenceStateRepository`): owns a
  `FusedLocationProviderClient` (already a dependency via `GeofenceLocationMonitor`), exposes a
  single `StateFlow<LatLon?>`. `refreshOnce()` is a one-shot `LocationHelper.lastKnownLocation()`
  read (unchanged semantics, just centralized); `startContinuous()`/`stopContinuous()` arm/disarm
  an active `LocationRequest` (`PRIORITY_BALANCED_POWER_ACCURACY`, 10s interval / 5s min),
  mirroring `GeofenceLocationMonitor`'s existing shape but left fully separate (different
  lifecycle/purpose — background significant-change re-ranking vs. foreground live tracking —
  explicit scope decision not to share the client instance).
- `MapViewModel`: its own `location: MutableStateFlow` is gone, `uiState`'s combine now reads
  `locationRepository.location` directly (continuous — Map is the one surface where a live
  position matters). New `startContinuousLocation()`/`stopContinuousLocation()` delegate straight
  to the repository. `MapScreen.kt`: new `DisposableEffect(lifecycleOwner)` calls
  `startContinuousLocation()`/`stopContinuousLocation()` on `ON_RESUME`/`ON_PAUSE` — since
  `MapViewModel` is hoisted at the `FreizeitApp` level and outlives tab switches, only the
  composable's own lifecycle knows when Map is actually the visible tab. Re-entering the Map tab
  replays `ON_RESUME` (`Lifecycle.addObserver` synchronously syncs a fresh observer up to the
  current state), which is also what fixes "switching to Map doesn't refresh location" — the same
  mechanism HomeScreen already used for its own resume refresh (#34). The existing "locate me"
  FAB's `refreshLocation()` call is untouched (already forced a fresh read; now goes through the
  repository).
- `HomeViewModel`/`CheckInViewModel`: `location` stays a local `MutableStateFlow`, but
  `refreshLocation()` now calls `locationRepository.refreshOnce()` then takes a one-time
  *snapshot* of `locationRepository.location.value` — deliberately not a continuous collection of
  the shared flow, so Map's background stream (or Check-in's new pull-to-refresh) can never
  reshuffle Home's swipe deck mid-session (#34's guarantee, explicitly re-verified during the
  grill-me session as the one real tension with #40's ask).
- `CheckInSearchScreen.kt` gains two things it never had before: a `DisposableEffect`/`ON_RESUME`
  observer identical to Home's (this screen previously only refreshed once via permission grant,
  so its distances/duration badges could be arbitrarily stale), and a Material3
  `PullToRefreshContainer`/`rememberPullToRefreshState()` wrapped around the results area (search
  results, favorites-nearby quick-picks, and the "no location" hint all share one `Box`) as a
  manual fallback — matches the user's established preference for always-available manual
  controls alongside automatic triggers. Confirmed the exact API shape against the project's
  resolved Material3 1.2.1 AAR directly (`PullToRefreshState.isRefreshing`/`startRefresh()`/
  `endRefresh()`/`nestedScrollConnection`, `PullToRefreshContainer`, `rememberPullToRefreshState()`
  — `PullToRefreshBox` doesn't exist until 1.3.0) before writing any code, same verify-before-
  relying-on-it approach as the date/time picker session's `DatePickerDialog`/`TimePicker` check.
  Since `refreshLocation()` is fire-and-forget (launches its own coroutine, doesn't suspend until
  done), the refresh indicator holds for a fixed 300ms (`PULL_TO_REFRESH_MIN_SPIN_MS`) rather than
  truly awaiting completion — pragmatic given a last-known-location read is near-instant anyway,
  avoids adding a second suspend-returning API just for this.
- `MapViewModel`/`HomeViewModel`/`CheckInViewModel` constructors: `appContext: Context` param
  replaced by `locationRepository: LocationRepository` in all three (each `Factory` updated to
  pass `app.container.locationRepository`); `LocationHelper` import dropped from all three
  ViewModels (still used as-is by `MapScreen.kt`/`CheckInSearchScreen.kt` for the unrelated
  permission-check flow, untouched).
- Tests: 160 total, 0 failures (unchanged — no test file needed changes; this issue's scope is
  pure ViewModel/Compose wiring around already-tested pure functions, none of which changed
  signature). `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/
  `assembleDebug`: all clean, no new warnings (the two pre-existing ones —
  `CheckInViewModel.kt`'s `FlowPreview` opt-in and `PoiMap.kt`'s unused `customNames` param — are
  both unchanged from before this session).
- Not verified on device: the entire continuous-stream/lifecycle wiring (Map's GPS stream actually
  starting/stopping on tab switch and app background/foreground, the "locate me" FAB still
  recentering correctly, Check-in's new resume refresh and pull-to-refresh indicator, and Home's

  platform/Compose wiring with no prior on-device confirmation — needs a real run on Robert's

## 2026-07-30 — Issue #19: swipe-deck flicker fix

- Not picked from the tracker cold — diagnosed live with the user via `/grill-me` against a
  specific repro (swiping Home's suggestion deck one direction briefly flashes a stale, unrelated
  card before landing on the correct one; the other direction never does), then implemented that
  fix. Addresses only issue #19's third bullet ("Flicker is still there when swiping through card
  deck"); its other two bullets (remove fading animation, wrap_content sizing) are untouched and
  out of scope for this session — closed anyway per the user's explicit instruction after
  confirming the flicker fix on device; re-file the other two separately if still wanted.
- Root cause, confirmed with the user before touching code: `SwipeableSuggestionCard`
  (`HomeScreen.kt`)'s window is always emitted in a fixed `[previousCard, nextCard, card]` order,
  and later Box children paint on top of earlier ones — deliberately, so `nextCard`'s idle peek
  sliver (not `previousCard`'s identical one) is what shows as the deck's "stackable" affordance
  at rest. But that static order held during an active drag too: revealing `previousCard` grows
  it past `nextCard`'s small idle-peek footprint, and since `nextCard` is emitted after (so always
  painted above) `previousCard`, `nextCard`'s idle sliver stayed visible on top of the growing
  card for the whole reveal — reads as a wrong-card flash that self-corrects once the drag commits
  and the window recomputes. Only affects revealing `previousCard`, matching the reported
  direction asymmetry: revealing `nextCard` never has this problem since the idle card
  (`previousCard`) is the one underneath in that case.
- Fix: added `isRevealTarget`/`revealZIndex` (pure, alongside the existing
  `topCardAlpha`/`revealProgress`/`isPastSwipeThreshold`) and wired `Modifier.zIndex()` into both
  branches of the per-entry modifier — current always highest, then whichever neighbor the drag is
  actively revealing, then the idle one. Deliberately zIndex rather than reordering the `window`
  list itself: reordering keyed children every drag frame is exactly the kind of churn the
  existing "one keyed window, stable call site" state-preservation design (see the long comment
  above `window`) was written to avoid; zIndex changes paint order without touching emission order
  or the keyed slots, so it's a strictly additive, orthogonal fix.
- Tests: 297 total, 0 failures (4 new `HomeSwipeDeckMathTest` cases for the two new pure
  functions). `compileDebugKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean.
- Verified on device by the user: the flash is gone.
