## 2026-09-07 — Issue #48: Manual POI adding: check-in and favorite parity for custom POIs

- Picked from the "Manual POI adding" epic (#43): #45 (the foundational slice) closed since the
  last session, unblocking #46/#47/#48. Of those three, #48 was the highest-impact pick — it's the
  only one where a custom POI is currently *invisible* to core app flows (geofence auto check-in,
  check-in search) rather than just missing a UI nicety, and it unblocks #49 (reimport-time merge
  detection, which additionally depends on #48). Already fully resolved in the issue body (per the
  epic's established convention of pre-resolving specs before filing), no `/grill-me` needed.
- Verdict/favorite parity needed no code change — confirmed, not just assumed: `#45`'s session
  already made this work as a side effect of `VerdictDao.setVerdict` operating on whatever `Poi` a
  caller passes in ( `CustomPoi.toPoi()` produces one), so a new
  `setVerdict works identically for a custom poi projected via toPoi` case was added to
  `VerdictDaoTest.kt` to lock that claim in as tested rather than leave it "probably fine."

  `poiDao`/`PoiDao.observeFavorites()` directly instead of through the Map screen's existing
  merged-list pattern (`MapViewModel.poisVerdictsAndNames`). New shared
  `data/repository/PoiLookup.kt` gives every other consumer the same fold, without duplicating it

  a new mirroring `CustomPoiDao.observeFavorites()` — same verdict-join query, over `custom_poi`)
  and `findPoiById` (routes on `isCustomPoiId` to `poiDao.getById`/`customPoiDao.getById()?.toPoi()`
  — an id is only ever in one of the two tables by construction, so this is an either/or, not a
  fallback probe).
- Geofence registration: `FreizeitApplication.kt`'s favorites-changed collector and
  `AppContainer.kt`'s `geofenceLocationMonitor` callback both swap their bare
  `poiDao.observeFavorites()` for `observeAllFavorites`/`allFavoritesOnce` — a favorited custom POI
  now gets a Play Services geofence registered exactly like an OSM favorite.
  `GeofenceSyncManager` gained a `CustomPoiDao` constructor dependency so `replaySelection` (the
  >100-favorites replay path) can resolve a persisted selected id back to a `Poi` via
  `findPoiById` regardless of which table it's actually in.
- Geofence transition handling: `GeofenceBroadcastReceiver`'s three direct `poiDao.getById(...)`
  call sites (`handleCheckIn`'s notification-action check-in, `refreshNotification`'s dwelling-id
  candidate resolution, and its final closest-favorite lookup before showing the notification) all
  switched to `findPoiById` — a DWELL/notification-check-in flow now resolves a custom POI the same
  way it already resolved an OSM one, no separate branch.
- `CheckInViewModel`: new private `allPois` flow folds `customPoiDao.observeAll().map { it.toPoi() }`
  into `poiDao.observeAll()` (mirrors `MapViewModel`'s identical merge), feeding both
  `favoritesNearby` and search — `CheckInSearchScreen.kt` itself needed zero changes since it only
  ever reads `CheckInViewModel.uiState`, never a DAO directly (confirmed before writing any UI
  code, not assumed).
- Tests: 351 total, 0 failures. New `PoiLookupTest.kt` (`findPoiById` resolving each table plus an
  unknown-id-in-either-table case; `observeAllFavorites`/`allFavoritesOnce` merging and correctly
  excluding an un-favorited custom POI) and the `VerdictDaoTest.kt` case above.
  `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean,

## 2026-08-05 — Issue #45: Manual POI adding — add custom POI via drop-pin

- Picked from five open `ready-for-agent` "Manual POI adding" issues (#45-#49, all children of
  epic #43): #45 is the only one with no `Blocked by`, and #46/#47/#48 all list `Blocked by: #45`
  (#49 additionally blocks on #48) — picked as the foundational vertical slice the other four
  build on, per the issue body's own spec (no `/grill-me` needed, already fully resolved).
- New `custom_poi` Room table/entity (`data/entity/CustomPoi.kt`) mirroring `Poi`'s fields, added
  via `MIGRATION_6_7` (version 6→7) — deliberately untouched by `PoiRepository.importFrom`'s
  markAllMissing→upsertAll→deleteUnverdictedMissing cycle, same rationale as the existing
  `PoiCustomName` precedent. Unlike `Poi`, `name`/`category` are non-null (required at creation

  `isCustomPoiId()`) — guaranteed never to collide with OSM's `node/`/`way/`/`relation/` ids, and
  the `custom/` prefix is there specifically so #47's later edit/delete-only-for-custom-POIs check
  can tell the two apart without a DB round trip.
- Merge strategy (the key architectural call): `CustomPoi.toPoi()` (`data/entity/CustomPoi.kt`)

  to that combine, not for any merge-specific reason. Favoriting a custom POI from the detail sheet
  already works today as a side effect of this merge (`setVerdict` operates on whatever `Poi` the
  sheet was given) — issue #48's actual remaining scope is narrower than its title suggests: just

  read `poiDao` directly instead of through this merged list.
- Add-POI flow, driven by a new FAB on `MapScreen` (state machine lives in `MapViewModel` as
  `AddPoiStep` — NONE/PLACING_PIN/FORM, plus `addPoiCenter: StateFlow<LatLon?>`):
  - `PLACING_PIN`: `PoiMap` gained an `addPoiActive`/`onCameraIdle` pair — while active, every
    camera-idle event (plus one fired immediately on entry, via a `LaunchedEffect(addPoiActive)`,

    the map's current center to `MapViewModel.updateAddPoiCenter`. The crosshair itself

    match sits within 40m; confirming or skipping the dialog both call `MapViewModel.saveCustomPoi`.
  - The Map screen's empty-state text ("No places yet...") used to replace the whole `PoiMap`
    composable when both `pois`/`allPois` were empty — changed to float on top of an always-mounted
    map instead, since the "Add place" FAB (and the map it pin-drops against) needs to be reachable
    even on a fresh install with no `.pbf` import yet; this was a real gap, not scope creep; the
    FAB/pin-drop mechanics literally didn't exist to reach otherwise in that state.
- Backup (`BackupJsonCodec`/`BackupRepository`/`BackupData`): `custom_poi` is now exported/restored

## 2026-08-02 — Issue #44: Check-in history date-bucketed sections

- Spec was fully resolved via `/grill-me` before this pickup (bucket priority order, calendar-
  based vs rolling windows, locale week start, sticky inert headers, per-row timestamp format by
  section, empty-bucket hiding) — posted to #44, implemented directly from it with no further
  clarification needed.
- New pure function `bucketVisits` (`util/CheckInHistoryBuckets.kt`): groups a `List<Visit>` into
  `VisitSection(label, visits)` buckets — Today, This week, Last week, This month, Last month,
  then one "March 2026"-style bucket per older month — using `WeekFields.of(locale)` for the week
  start rather than a rolling 7-day window, so results genuinely change with device locale (US
  Sunday-start vs. UK/DE Monday-start). Relies on `visits` already being sorted newest-first (as
  `VisitDao.observeAll()` returns it) and on the bucket windows being non-overlapping,
  chronologically decreasing intervals: grouping in encounter order via a `LinkedHashMap` yields
  correctly-prioritized, already-deduped section order for free, no separate sort/priority-list
  step needed. Year rollover (a December visit bucketed while "now" is January) falls out of
  plain `LocalDate` month arithmetic (`minusMonths`, `YearMonth.from`) rather than needing
  special-cased logic — verified with a dedicated test rather than assumed.
- Per-row timestamp reformatted now that headers carry the date (`util/DateTimeFormat.kt`): new
  `formatVisitTimeOnly` (time only, e.g. "3:45 PM", for the Today section) and
  `formatVisitWeekdayAndTime` ("Tue, 3:45 PM", every other section) sit alongside the existing
  `formatVisitTimestamp` (full medium date+time) rather than replacing it — that one's still used
  by `CheckInDateTimeFlow.kt`'s confirmation screen, out of this issue's scope.
- `CheckInScreen.kt`: `LazyColumn`'s flat `items(state.visits)` replaced with a `sections.forEach`
  loop emitting one `stickyHeader` (new `SectionHeader` composable — inert `Surface`+`Text`, no
  click handling) per bucket followed by that bucket's `items(section.visits)`. `stickyHeader` is
  a direct `LazyListScope` member (not an extension needing its own import, unlike `items`) —
  initially imported it as one anyway and hit an "Unresolved reference" compile error before
  catching the mistake. `VisitRow` now takes the pre-formatted `timestampText` as a param instead
  of formatting `visit.visitedAt` itself, so the Composable doesn't need to know which section
  it's in beyond what the caller already decided. Headers are naturally invisible to
  `CheckInHistoryViewModel`'s existing select/delete/undo logic since that only ever operates on
  `Visit.id` values coming from `items`, never from the sections list — no ViewModel changes
  needed, as the issue predicted.
- Tests: new `CheckInHistoryBucketsTest.kt` (13 cases) covering today-vs-this-week priority, week/
  month boundaries, the week-start locale-variation case explicitly (same visit date buckets as
  "Last week" under `Locale.UK` but "This week" under `Locale.US`), locale-formatted month-year
  labels (`Locale.GERMANY` → "Mai 2026"), both year-rollover shapes (a December visit reads "Last
  month" in early January; a November visit two months back keeps "November 2026", not
  "November 2027"), empty-bucket omission, and section-order-follows-priority given already-
  sorted-desc input. 321 total tests, 0 failures. `compileDebugKotlin`/
  `compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean.
- Not verified on device: sticky-header pinning behavior and the header's opaque background
  actually occluding rows scrolling underneath it are Compose layout behavior no unit test
  exercises — worth a real scroll-through on Robert's phone, along with a visual check that the
  section header's `labelLarge`/`onSurfaceVariant` styling reads clearly against the list.

## 2026-08-01 — Issue #42: active-notification bugs

- Issue was a live bug report (unfavorited place still notified; two DWELL notifications arriving
  20min/1.5h after the fact) — root-caused via a `/grill-me` session before any code was touched
  (scope: both bugs in one pass; where the stale-favorite fix lives; whether to reconcile the live
  notification immediately and how, given no location fix is available on that path; which
  location API to use for the staleness check within `goAsync()`'s time budget; threshold/fail-
  open behavior; testing approach), posted to #42 as a comment, then implemented directly from
  that spec.
- Root cause 1 (stale favorite): `GeofenceSyncManager.register()` diffed registered geofences
  against current favorites and removed stale ones, but never touched
  `GeofenceStateRepository.dwellingPlaceIds`. An unfavorited-while-dwelling place has no geofence
  left to ever send an EXIT, so its id stayed "dwelling" forever — able to win
  `closestEligibleFavorite()` (and thus show a notification, or block a legitimate one) on any
  later, unrelated transition.
- Root cause 2 (late delivery): Play Services can delay a DWELL broadcast well past the requested
  `NOTIFICATION_RESPONSIVENESS_MILLIS` under Doze/standby batching — the event's own
  `triggeringLocation` reflects the real transition moment, not delivery time, so it can't detect
  this.
- New pure functions in `util/GeofenceNotificationSelection.kt` (tested in
  `GeofenceNotificationSelectionTest.kt`, 172 tests total / 0 failures):
  `reconcileDwellingOnUnregister(dwellingPlaceIds, idsToRemove, activeNotificationPlaceId)` — purges
  removed ids from dwelling state, flags whether the currently-shown notification (if any) needs
  cancelling; `isNotificationStale(currentLat/Lon, accuracyMeters, poiLat/Lon, radiusMeters)` —
  radius + accuracy-buffer distance check.
- `GeofenceStateRepository` gains `activeNotificationPlaceId` (nullable `stringPreferencesKey`):
  which favorite the single outstanding notification is for, so a favorites-change can tell
  whether it needs to cancel that specific notification.
- `GeofenceSyncManager.register()`: on each successful `removeGeofences()`, calls
  `reconcileDwellingState()` (new private helper) to purge + cancel-if-affected. No re-ranking is
  attempted here — no location fix available outside a geofence transition, so a still-dwelling
  favorite's notification is left alone for the next real transition to correct. `removeAll()` also
  clears `activeNotificationPlaceId` now, alongside the state it already cleared.
- `GeofenceBroadcastReceiver.refreshNotification()`: before showing a DWELL notification, checks
  `LocationHelper.lastKnownLocation()` (synchronous, cached — already used elsewhere in this
  codebase, no risk to `goAsync()`'s ~10s budget the way a fresh GPS fix would be) against the
  target favorite via `isNotificationStale`; suppresses (cancels) instead of showing if stale. No
  cached location → fails open (shows it) rather than silently dropping a legitimate notification.
  `showNotification`/`cancelNotification` helpers now wrap `GeofenceNotifications.show`/`cancel`
  to keep `activeNotificationPlaceId` in sync at every call site (`refreshNotification`,
  `handleCheckIn`, `ACTION_DISMISS`).
- `assembleDebug`/`testDebugUnitTest`: both clean, no new warnings.
- Not verified on device: the actual DWELL/EXIT timing and delivery-latency behavior this targets
  is inherently a real-device/real-Play-Services thing — needs confirmation on Robert's phone that
  (a) un-favoriting mid-dwell no longer resurfaces a notification for that place, and (b) a
  deliberately-delayed DWELL (e.g. airplane-mode trick) gets suppressed rather than shown.
