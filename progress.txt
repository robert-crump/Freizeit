## 2026-07-30 — Issue #19 (partial): swipe-deck flicker fix

- Not picked from the tracker cold — diagnosed live with the user via `/grill-me` against a
  specific repro (swiping Home's suggestion deck one direction briefly flashes a stale, unrelated
  card before landing on the correct one; the other direction never does), then implemented that
  fix. Addresses only issue #19's third bullet ("Flicker is still there when swiping through card
  deck"); its other two bullets (remove fading animation, wrap_content sizing) are untouched and
  out of scope for this session, so the issue stays open rather than closing.
- Root cause, confirmed with the user before touching code: `SwipeableSuggestionCard`
  (`HomeScreen.kt`)'s window is always emitted in a fixed `[previousCard, nextCard, card]` order,
  and later Box children paint on top of earlier ones — deliberately, so `nextCard`'s idle peek
  sliver (not `previousCard`'s identical one) is what shows as the deck's "stackable" affordance
  at rest. But that static order held during an active drag too: revealing `previousCard` grows
  it past `nextCard`'s small idle-peek footprint, and since `nextCard` is emitted after (so always
  painted above) `previousCard`, `nextCard`'s idle sliver stayed visible on top of the growing
  card for the whole reveal — reads as a wrong-card flash that self-corrects once the drag commits
  and the window recomputes. Only affects revealing `previousCard`, matching the reported
  direction asymmetry: revealing `nextCard` never has this problem since the idle card
  (`previousCard`) is the one underneath in that case.
- Fix: added `isRevealTarget`/`revealZIndex` (pure, alongside the existing
  `topCardAlpha`/`revealProgress`/`isPastSwipeThreshold`) and wired `Modifier.zIndex()` into both
  branches of the per-entry modifier — current always highest, then whichever neighbor the drag is
  actively revealing, then the idle one. Deliberately zIndex rather than reordering the `window`
  list itself: reordering keyed children every drag frame is exactly the kind of churn the
  existing "one keyed window, stable call site" state-preservation design (see the long comment
  above `window`) was written to avoid; zIndex changes paint order without touching emission order
  or the keyed slots, so it's a strictly additive, orthogonal fix.
- Tests: 297 total, 0 failures (4 new `HomeSwipeDeckMathTest` cases for the two new pure
  functions). `compileDebugKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean.
- Not verified on device: the actual visual fix (does the flash genuinely disappear on a real
  phone, dragged at realistic speed) has no on-device confirmation yet — the diagnosis and fix
  were validated via the pure z-order/paint-order reasoning the user confirmed, not a device run.

## 2026-07-26 — Issue #32: POI search: Focus jumps back to first position while typing

- Design worked out via a full /grill-me pass before writing any code (fix scope, debounce
  parity with Explore, shared-vs-duplicated constant, test coverage, clear-button debounce
  tradeoff, rememberSaveable vs remember, device-verification ownership — all resolved with
  the user first, same approach as #21).
- Root cause: `CheckInScreen.kt`'s `OutlinedTextField` bound `value` directly to
  `state.searchQuery`, which round-trips through `CheckInViewModel`'s un-debounced 5-way
  `combine` (including `poiDao.observeAll()`) on `Dispatchers.Default` before echoing back —
  Compose can't reconcile the cursor position against a stale/delayed value, so it resets to
  the start. Identical bug already fixed in `ExploreScreen`'s search (`10ac5d3`) via a local
  `rememberSaveable` buffer decoupled from ViewModel state; Check-in's search bar (added later
  in #30) never got the same treatment.
- Fix mirrors Explore's pattern exactly rather than diverging: `CheckInScreen.kt` gained a
  local `searchText` (`rememberSaveable`) driving the text field, with `onValueChange`/
  `onClear` updating both the local buffer and the ViewModel. `CheckInViewModel.kt` gained its
  own private `SEARCH_DEBOUNCE_MS = 250L` (deliberately duplicated, not shared with
  `ExploreViewModel`'s constant of the same name/value, so the two screens stay independently
  tunable) and `.debounce(SEARCH_DEBOUNCE_MS)` on the `searchQuery` flow feeding the `combine`.
- Deliberately not special-cased: `clearSearch()` still goes through the same debounced flow,
  so Check-in's clear button carries the same ~250ms lag before reverting to the
  favorites-nearby list that Explore's clear button already has — an accepted existing
  tradeoff from the pattern being mirrored, not something to fix differently per screen.
- No new test: cursor/focus behavior isn't practically unit-testable without a Compose UI test
  harness (this codebase has none), and Explore's identical fix shipped with no test either —
  same precedent followed rather than introducing new test infrastructure as a side effect of
  a one-issue bug fix.
- Tests: 140 total, 32 failed — identical count and failures to unmodified `main` (confirmed

  pre-existing Robolectric `UnsatisfiedLinkError` failures (documented since #10/#13/#15/#23)

- Picked up on explicit user override: #29 is the only `ready-for-agent` issue, but its

- Split `GeofenceSyncManager`'s single `sync()` into two: `sync(enabled, favorites)` (unchanged
  trigger — favorites/toggle change, app-open) and a new `rerank(enabled, favorites, location)`.
  Under 100 favorites, `sync()` still registers everyone immediately, unchanged from #28. Over
  100, `sync()` doesn't rank anything itself — it replays whichever closest-100 selection the
  last `rerank()` persisted to a new `GeofenceStateRepository.selectedFavoriteIds` (same
  DataStore-backed `Set<String>` pattern as the existing `insidePlaceIds`). `rerank()` is the
  only thing that ever recomputes that set, and it's wired to fire from exactly one place: a new
  `GeofenceLocationMonitor` (`FusedLocationProviderClient.requestLocationUpdates` with
  `setMinUpdateDistanceMeters(500f)`, no periodic interval logic beyond Play Services' own
  batching) — armed/disarmed in `FreizeitApplication.onCreate` alongside the same
  `autoCheckInEnabled` collector that already drives `sync()`, so it's never triggered by app-open
  or a timer, per the issue's explicit ask.
- Ranking itself is a new pure function, `selectClosestFavorites(favorites, lat, lon, limit)` in
  `util/GeofenceFavoriteRanking.kt` (Haversine via the existing `GeoDistance.metersBetween`,
  matching `rankNearbyForCheckIn`'s existing pure-function-for-testability convention) — under
  `limit` returns the list unchanged, over it sorts by distance and takes `limit`.
- Lazy un-favorite deregistration (explicit AC: "not required to be immediate") falls out of how
  `sync()`'s replay path resolves ids: it looks each persisted selected id up via
  `PoiDao.getById()` directly, not by filtering the current `favorites` param against it — so an
  id that's no longer a favorite still resolves (the `Poi` row survives un-favoriting, only the
  `Verdict` row changes) and keeps its geofence registered until the next `rerank()` overwrites
  the whole selected-ids set from scratch and drops it.
- First-time-crossing-100 bootstrap (no `rerank()` has ever run, no persisted selection to
  replay): `sync()` falls back to `favorites.take(100)` in arbitrary DB order rather than doing
  any location-based ranking itself — deliberately dumb, to keep `sync()` truly rank-free per the
  issue's "not on app-open" requirement; a real closest-100 selection supersedes it as soon as
  the location monitor's first significant-change fix arrives.
