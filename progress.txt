## 2026-09-07 — Issue #49: Manual POI adding: reimport-time merge detection and confirmation

- Picked via `/next-issue issue 49` (user-specified). Confirmed `ready-for-agent` and unblocked
  (#45/#48 both closed). Already fully resolved in the issue body per the epic's established
  convention; no `/grill-me` needed. This is the last open issue in the "Manual POI adding" epic
  (#43) — #46/#47/#48/#49 are all now closed.
- New `util/NameSimilarity.kt` (pure, no existing helper to reuse per the exploration pass):
  normalizes (lowercase, collapse non-alnum runs to a single space) then matches on exact
  equality, substring containment either direction, or a normalized-Levenshtein similarity ratio
  above a threshold (0.6 default) — the "fuzzy substring/edit-distance" the issue asks for.
  New `util/CustomPoiMergeMatch.kt` layers this on top of the same distance+category shape as
  `CustomPoiProximity` (#45/#47) — reuses `GeoDistance`, same 40m threshold constant — but adds
  the name check `CustomPoiProximity` deliberately doesn't have (that one's a same-category-only
  dedup warning; #49 needs a real place-identity signal before ever proposing a merge). Yields at
  most one `MergeCandidate` per custom POI (its nearest qualifying match), so "no candidates"
  falls out naturally when nothing clears both thresholds.
- `PoiRepository.importFrom` now returns a new `ImportResult(count, mergeCandidates)` instead of
  a bare `Int` — candidates computed once the transaction commits, against `parsed.pois` (exactly
  what was just upserted) and a fresh `customPoiDao().getAll()`. New
  `PoiRepository.mergeCustomPoiInto(customPoiId, poiId)`: one `db.withTransaction` re-keying the
  Verdict (new `VerdictDao.rekey`, `UPDATE OR REPLACE` since `placeId` is that table's primary
  key — the rare case the target OSM place already had its own verdict is resolved in the custom
  POI's favor) and every Visit (new `VisitDao.rekey`, plain `UPDATE`, no PK conflict since `id` is
  the actual primary key there) onto the matched `poi.id`, then deletes the `custom_poi` row —
  deliberately the mirror image of `MapViewModel.commitPendingDelete` (#47), which deletes those
  rows outright instead of re-keying them; that method's doc comment already named #49 as the
  future contrast.
- `SettingsViewModel` gained a `mergeCandidates: StateFlow<List<MergeCandidate>>` (populated
  alongside `ImportStatus.Success` in `importPoiFile`) plus `confirmMerge`/`dismissMerge`, both of
  which pop the front entry — `SettingsScreen` renders only `mergeCandidates.firstOrNull()` as an
  `AlertDialog` (the existing two-button `confirmButton`/`dismissButton` shape already used for
  the auto-check-in disclosure dialog), so several candidates from one import walk through as a
  sequence of single dialogs rather than needing new stacked-dialog UI. Per the issue's explicit
  "no additional undo" — confirming just calls `mergeCustomPoiInto` and dismissing is a pure
  state-list edit, no Snackbar/undo path like #47's delete.
- Tests: 257 total, 0 failures. New `NameSimilarityTest.kt`, `CustomPoiMergeMatchTest.kt` (mirrors
  `CustomPoiProximityTest.kt`'s GeoDistance-derived-offset convention), `VerdictDao`/`VisitDao`
  `rekey` cases (including the already-has-a-verdict/visits-at-the-target-id edge cases), and
  `PoiImportTest.kt` additions covering `importFrom` surfacing (and not surfacing) candidates plus
  `mergeCustomPoiInto`'s full re-key-then-delete transaction end to end.
  `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean,
  no new warnings.

  Confirmed `ready-for-agent` and unblocked (#45 closed); already fully resolved in the issue body

- New `data/geocoding/NominatimClient.kt` (object, mirrors `OpenMeteoClient`'s exact pattern: plain
  `HttpURLConnection` + Gson, one GET per search, null-on-any-failure) plus a new
  `domain/geocoding/GeocodeResult.kt` (lat/lon/displayName/street/housenumber/postcode/city — the

  Python. User-Agent identifies the app + repo URL rather than a personal contact address — real
  per Nominatim's usage policy (a default HttpURLConnection one is rejected) without sending any
  user-identifying data to this third-party service.
- UI lives in `AddPoiPinOverlay` (the pin-drop step), not the form: a new `AddressSearchBar`
  private composable — `OutlinedTextField` + explicit "Search" button/IME action (no live-
  typeahead, respects Nominatim's 1 req/sec policy without debounce logic), permanent "©
  OpenStreetMap contributors" caption beneath it, and a results `Card` below that. Selecting a
  result re-centers the pin by reusing the existing `MapViewModel.focusOn` camera-jump path (its

  new `pendingAddressPrefill` StateFlow. `AddPoiForm` gained a `prefillAddress: GeocodeResult?`

- `MapViewModel` gained `AddressSearchState` (query/results/isSearching/error/searched — `error`
  vs. an empty `results` list are distinct so the empty-state message only shows after a genuine
  zero-match search, not a network failure) plus `updateAddressSearchQuery`/`searchAddress`/
  `selectAddressResult`. `searchAddress`'s IO-dispatched response checks the query hasn't changed
  since the request fired before applying it (mirrors `selectPoi`'s existing late-response guard)
  rather than adding a generation counter. Both new StateFlows are cleared in `cancelAddPoi` and
  `saveCustomPoi` alongside the existing `addPoiCenter`/`editingCustomPoi` resets.

  `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean,

## 2026-09-07 — Issue #50: Deep-link Home to a specific place's detail sheet

- Picked from the widget epic (design discussion referenced by #51-#56): of the two entirely
  unblocked issues (#50, #51) plus the two remaining Manual POI adding leftovers (#46, #49, both
  ready since #45/#48 closed), #50 was the highest-impact pick — it's foundational plumbing that
  #52 depends on, has no new Gradle dependency to introduce (unlike #51's Glance widget, a much
  bigger single slice better left as its own pickup), and is fully self-contained/independently
  testable per the issue's own spec. Already fully resolved in the issue body per the epic's
  established convention; no `/grill-me` needed.
- `MainActivity` gained a `mutableStateOf<String?>` `targetPoiId`, read from a new
  `EXTRA_TARGET_POI_ID` intent extra in `onCreate` and re-read in a new `onNewIntent` override
  (calls `setIntent` first) — a `mutableStateOf` rather than a plain `var` specifically so a
  relaunch delivered to an already-running Activity (e.g. a future widget tap using
  `FLAG_ACTIVITY_SINGLE_TOP`) recomposes `FreizeitApp` with the new value instead of only ever
  taking effect on a cold start.
- `FreizeitApp` takes the new `targetPoiId` param and holds it in `pendingTargetPoiId`
  (`rememberSaveable(targetPoiId)`, so it resets whenever a *new* incoming value arrives but
  otherwise survives ordinary recompositions), passed to `HomeScreen` alongside an
  `onTargetPoiIdHandled` callback that clears it back to null — this is what stops the sheet from
  reopening on a later tab revisit, since `HomeScreen`'s own composable lambda re-executes fresh
  each time Home re-enters the NavHost.
- `HomeScreen` resolves the id via a new `LaunchedEffect(targetPoiId)` (fires once per distinct
  non-null value, satisfying the issue's "once, not on every recomposition/resume") calling
  `HomeViewModel.openTargetPoi`, then immediately invokes `onTargetPoiIdHandled`. The sheet itself
  reuses `PlaceDetailSheet` as-is (its own doc comment already claimed "opened from map markers,
  list rows, and Home cards" — Home didn't actually do this yet before this session; now it does)
  rather than building a second detail view.
- `HomeViewModel.openTargetPoi` mirrors `MapViewModel.selectPoi`'s pattern: resolves the id via
  the existing `findPoiById` (#48's `PoiLookup.kt`, already covers both `poi`/`custom_poi` tables
  and is already unit-tested), computes distance against the current cached location via
  `GeoDistance.metersBetween` (already unit-tested), and looks up `lastVisitLabel`. An id that
  doesn't resolve (deleted place, stale/bad extra) just returns early — `targetPoi` stays null and
  Home renders normally, no crash, per the issue's explicit acceptance criterion. `HomeViewModel`
  also gained a `setCustomName` (mirroring `MapViewModel`'s) since `PlaceDetailSheet` requires a
  non-null `onCustomNameChange` callback — `HomeViewModel`'s existing `poiCustomNameDao` and a new
  `customPoiDao` constructor dependency (added to `HomeViewModel.Factory`, same
  `app.container.database.customPoiDao()` source `MapViewModel.Factory` already uses) make this
  possible with no new DB access needed.
- Tests: 217 total, 0 failures — no new tests, deliberately: this issue is orchestration/wiring
  over primitives that are already unit-tested (`findPoiById`/`PoiLookupTest.kt`,
  `GeoDistance.metersBetween`/`GeoDistanceTest.kt`), the same reasoning `MapViewModel.selectPoi`
  (which this mirrors) was never itself given a dedicated test either.
  `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean,
  no new warnings.
- Not verified on device: the actual deep-link launch (`adb shell am start -n

## 2026-09-07 — Issue #47: Manual POI adding: edit/delete custom POI, with undo

- Picked from the "Manual POI adding" epic (#43): of the three remaining open issues (#46/#47/#49,
  all unblocked now that #45/#48 are closed), #47 was the highest-impact pick — it's the only one
  of the three fixing a real gap in already-shipped functionality (a custom POI, once created, has
  no way to fix a typo or remove one added by mistake) rather than adding a new capability on top
  (#46's address search, #49's reimport merge-detection). Also the best fit for the user's own
  stated preference for undo/safety-net affordances on destructive actions (see
  `feedback-ux-safety-nets.md`). Already fully resolved in the issue body per the epic's
  established convention; no `/grill-me` needed.
- Edit and Delete actions added to `PlaceDetailSheet` (`onEdit`/`onDelete`, both nullable — omitted
  entirely, not shown disabled, for an OSM-sourced `Poi`); `MapScreen` only ever passes non-null
  callbacks when `isCustomPoiId(item.poi.id)`.
- Edit reopens `AddPoiForm` pre-filled via new `Poi.toCustomPoi()` (`CustomPoi.kt`) — the exact
  reverse of the existing `toPoi()` projection, round-trip-tested in `CustomPoiTest.kt` — skipping
  pin-placement entirely (the location itself isn't editable here, only the form fields) and
  saving through the existing `id` rather than minting a new one. `AddPoiForm` gained an `initial:
  CustomPoi? = null` param seeding every field; the id-preservation logic itself was pulled out
  into a new pure `buildCustomPoiCandidate()` (mirroring this file's own convention of extracting
  pure logic for testability) and unit-tested directly (`BuildCustomPoiCandidateTest.kt`) rather
  than only through Compose. `CustomPoiProximity.findNearbyMatch` gained an `excludeId` param so
  editing in place (same lat/lon, unchanged) doesn't trip its own "already exists" warning against
  itself — regression-tested in `CustomPoiProximityTest.kt`.
- Delete is optimistic per the issue's spec: `MapViewModel.requestDeleteCustomPoi` sets a new
  `pendingDeleteCustomPoiId` and closes the sheet; `poisVerdictsAndNames`' merge now runs a new
  pure `excludePendingDelete()` (unit-tested in `PendingCustomPoiDeleteTest.kt`) so the marker
  disappears from the map/search instantly while the `custom_poi`/`Verdict`/`Visit` rows are
  untouched in the DB. Since nothing is actually deleted yet, `undoDeleteCustomPoi()` is just
  clearing that pending id back to null — "restoring" the Visit/Verdict needs no extra work because
  they were never removed. `MapScreen` shows a "Deleted — Undo" Snackbar (own `SnackbarHostState`,
  same `showSnackbar`+`SnackbarResult` pattern as `CheckInDateTimeFlow`'s check-in undo): Undo taps
  call `undoDeleteCustomPoi()`, a timeout/swipe-dismiss calls `commitPendingDelete()` (which deletes
  the Verdict, every Visit via new `VisitDao.deleteByPlaceId()`, then the `custom_poi` row itself,
  in that order). A `DisposableEffect(Unit)` in `MapScreen` also calls `commitPendingDelete()` on
  dispose, covering the spec's "or the user navigates away" case if the Snackbar never resolves on
  its own (e.g. switching bottom-nav tabs mid-countdown) — safe to call unconditionally since it
  no-ops once nothing is pending.
- Tests: 217 total (this repo's actual current count — noting it since the last two progress
  entries' claimed "351" doesn't match either `@Test` grep or the JUnit XML output, seemingly a
  stale/incorrect figure carried forward; not investigated further as out of scope for #47), 0

  `CustomPoiProximityTest.kt` cases (`excludeId`), two `VisitDaoTest.kt` cases
