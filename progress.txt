## 2026-07-26 — Issue #22: Investigate hardcoded Cologne fallback location in HomeViewModel

- Picked up on explicit user override: the issue carries no `ready-for-agent` label (no labels
  at all — filed as a self-assigned follow-up from #21, never triaged). Proceeded anyway since
  the user named it directly and it turned out to be fully specified once investigated.
- Answered the issue's three questions by reading code, not guessing:
  - **Interaction with #21's radius filter**: none. `HomeViewModel.uiState`'s `combine` block
    (`HomeViewModel.kt:110-138`) feeds `SuggestionEngine.withinRadius` the raw `loc` from the
    `location` `StateFlow` — real GPS fix or `null` — never the `FALLBACK_LAT`/`FALLBACK_LON`
    constants. `withinRadius` already treats `null` as "skip filtering" (its doc comment cites
    #21 directly). The fallback constants are read in exactly two places, both camera/fetch
    centering, never suggestion filtering: `HomeViewModel.refreshLocation()`'s
    `weatherRepository.refresh(...)` call and `PoiMap.kt`'s initial camera target.
  - **Why "Cologne" and whether it should exist at all**: it shouldn't have been Cologne —
    that was a bug, not a documented decision. `git log -S` traces `FALLBACK_LAT = 50.94` /
    `FALLBACK_LON = 6.96` (Köln's actual coordinates) to the 2026-07-06 v2-rewrite squash
    commit, which predates the POI extraction bbox decision entirely. `tools/poi_extraction`
    fixed the bbox to Aachen center +/-20km on 2026-07-16 (`4de3c36`, lat 50.5956-50.9550, lon
    5.7996-6.3682) and nobody circled back to the fallback constants. Cologne's longitude
    (6.96) sits outside the bbox's max lon (6.3682) — the old fallback pointed to a spot with
    zero POI coverage, so a no-GPS user would see an empty Explore map and get weather for a
    city ~60km from every POI in the app. The fallback itself should exist (better than 0,0 or
    a blank map/weather widget when GPS is unavailable) — only the coordinates were wrong.
  - Fixed both call sites (`HomeViewModel.kt`, `PoiMap.kt`) to the actual bbox center
    (50.7753, 6.0839 — Aachen), with comments naming the real source (`tools/poi_extraction`)
    instead of the incorrect "Cologne" label, and a note in `HomeViewModel.kt` cross-referencing
    #22 so the history of the mistake stays visible.
- No test references either fallback constant directly (checked `app/src/test` for
  `HomeViewModel`/`PoiMap`); the 50.94/6.96 literals in `SuggestionFixture.kt` and
  `OpenMeteoClientTest.kt` are unrelated fixture coordinates, not references to the constants.

## 2026-07-25 — Issue #29: Closest-100 geofence selection for large favorite counts

- Picked up on explicit user override: #29 is the only `ready-for-agent` issue, but its
  "Blocked by #28" note is a formal-tracker relationship, not a technical one — #28's code
  (`GeofenceSyncManager` registering every favorite, no cap) is already implemented and on
  `main` (confirmed by reading the file directly); #28's `ready-for-human` label is about its
  Play Store background-location policy surface, not about #29's prerequisite being unbuilt.
  Three prior sessions (#25/#26/#27's log entries) deferred #29 for this reason; the user
  explicitly asked to implement it regardless this time, confirmed live: "I already received a
  notification for a favorite nearby when the app was open" — i.e. #28's registration path is
  demonstrably working already.
- Split `GeofenceSyncManager`'s single `sync()` into two: `sync(enabled, favorites)` (unchanged
  trigger — favorites/toggle change, app-open) and a new `rerank(enabled, favorites, location)`.
  Under 100 favorites, `sync()` still registers everyone immediately, unchanged from #28. Over
  100, `sync()` doesn't rank anything itself — it replays whichever closest-100 selection the
  last `rerank()` persisted to a new `GeofenceStateRepository.selectedFavoriteIds` (same
  DataStore-backed `Set<String>` pattern as the existing `insidePlaceIds`). `rerank()` is the
  only thing that ever recomputes that set, and it's wired to fire from exactly one place: a new
  `GeofenceLocationMonitor` (`FusedLocationProviderClient.requestLocationUpdates` with
  `setMinUpdateDistanceMeters(500f)`, no periodic interval logic beyond Play Services' own
  batching) — armed/disarmed in `FreizeitApplication.onCreate` alongside the same
  `autoCheckInEnabled` collector that already drives `sync()`, so it's never triggered by app-open
  or a timer, per the issue's explicit ask.
- Ranking itself is a new pure function, `selectClosestFavorites(favorites, lat, lon, limit)` in
  `util/GeofenceFavoriteRanking.kt` (Haversine via the existing `GeoDistance.metersBetween`,
  matching `rankNearbyForCheckIn`'s existing pure-function-for-testability convention) — under
  `limit` returns the list unchanged, over it sorts by distance and takes `limit`.
- Lazy un-favorite deregistration (explicit AC: "not required to be immediate") falls out of how
  `sync()`'s replay path resolves ids: it looks each persisted selected id up via
  `PoiDao.getById()` directly, not by filtering the current `favorites` param against it — so an
  id that's no longer a favorite still resolves (the `Poi` row survives un-favoriting, only the
  `Verdict` row changes) and keeps its geofence registered until the next `rerank()` overwrites
  the whole selected-ids set from scratch and drops it.
- First-time-crossing-100 bootstrap (no `rerank()` has ever run, no persisted selection to
  replay): `sync()` falls back to `favorites.take(100)` in arbitrary DB order rather than doing
  any location-based ranking itself — deliberately dumb, to keep `sync()` truly rank-free per the
  issue's "not on app-open" requirement; a real closest-100 selection supersedes it as soon as
  the location monitor's first significant-change fix arrives.
- Tests: new `GeofenceFavoriteRankingTest` (5 cases — under limit unchanged, exactly-at-limit
  unchanged, over limit keeps exactly the closest N out of a shuffled 150-favorite fake set
  matching the issue's own "testable with >100 entries" acceptance criterion, over-limit results
  sorted closest-first, empty input). No test added for `GeofenceSyncManager`/
  `GeofenceLocationMonitor` themselves — both need a real Android `Context`/Play Services client,
  same reason the pre-#29 `GeofenceSyncManager` had no test file either.
  `compileDebugKotlin`: clean. `testDebugUnitTest`: 138 total (was 133), 28 failed (unchanged) —
  the +5 are the new `GeofenceFavoriteRankingTest` cases, all green (confirmed via its own XML
  report: 5/5 pass); the 28 failures are the same 6 pre-existing Robolectric
  `UnsatisfiedLinkError` classes documented since #10/#13/#15/#23

## 2026-07-25 — Issue #28: Auto-detect proximity notification for favorites

- Flagged `ready-for-human` (not `ready-for-agent`) in the issue itself —
  background location + a Play Store disclosure surface. Implemented with
  Robert pairing directly rather than picked up autonomously, which the
  next-issue skill's checklist treats as satisfying the same human-review
  intent the label exists for.
- No new `Favorite` entity, no new "last checked in" storage: favorites are
  already `PoiDao.observeFavorites()` (poi ⋈ verdict='favorite', #17), and
  the shared cross-source cooldown ("manual or notification, one clock per
  favorite") falls straight out of the existing `visit` table — added
  `VisitDao.lastVisitedAt(placeId)` (`MAX(visitedAt) WHERE placeId = ...`)
  instead of inventing a parallel timestamp store. `Visit.SOURCE_NOTIFICATION`
  added alongside the existing `SOURCE_MANUAL`.
- Geofence radius reuses `CheckInViewModel.CHECKIN_FAVORITE_RADIUS_METERS`
  (200m, #23) by direct import rather than redefining it, per the issue's
  own "same radius as the manual check-in list's 200m cutoff."
- New `com.example.freizeit.data.geofence` package: `GeofenceSyncManager`
  (registers/removes Play Services geofences — one per favorite, ENTER+EXIT
  transitions, `removeGeofences` then `addGeofences` on every resync since
  Play Services has no "update" call), `GeofenceBroadcastReceiver` (handles
  both the Play Services transition intent and the notification's own
  "Check in"/"Dismiss" action intents — one receiver so all three share the
  same "recompute the one active notification" path), `GeofenceNotifications`
  (channel setup + build/show/cancel).
- "Only the closest favorite's notification is ever shown" is solved
  structurally rather than by tracking per-favorite notification IDs: every
  notification reuses one fixed ID, so there is never more than one to begin
  with. What still needs tracking is *which* favorites the phone is
  currently physically inside (Play Services only tells you about the
  transition that just fired, not the standing set) — new
  `GeofenceStateRepository` persists that as a `Set<String>` of placeIds via
  DataStore, deliberately kept separate from `SettingsRepository` since it's
  runtime state, not a user-facing preference. On every ENTER/EXIT the
  receiver updates that set, then re-derives the nearest non-cooling-down
  member from the transition's `triggeringLocation` (pure, unit-tested
  `closestEligibleFavorite`/`isCoolingDown` in new
  `util/GeofenceNotificationSelection.kt`) and shows or cancels accordingly.
  A cooling-down closest favorite does NOT suppress the notification
  entirely — the next-nearest non-cooling-down one still gets it, since nothing
  in the issue text says a *whole spot* is picked before applying cooldown,
  only that "that favorite" is suppressed.
- Dismiss vs. cooldown, deliberately kept independent: `ACTION_DISMISS` only
  cancels the notification, touching neither the inside-set nor the visit
  log, so a fresh ENTER later can re-show it — matches "a dismissed or
  ignored notification does NOT suppress" without needing a "was dismissed"
  flag anywhere.
- Sync trigger: `FreizeitApplication.onCreate` launches a
  `combine(settingsRepository.autoCheckInEnabled, poiDao.observeFavorites())
  .distinctUntilChanged()` collector calling `GeofenceSyncManager.sync(...)`
  — covers the toggle flipping on (after #24's permission chain completes),
  favorites being added/removed, and process start (geofences don't survive
  process death the way a DataStore flag does, so re-registering on every
  cold start is required, not just an optimization).
- Added `com.google.android.gms:play-services-location:21.3.0` (this
  project's first Play Services dependency — MapLibre, not Google Maps, was
  already in use, so `google()` in `settings.gradle` existed but nothing
  had pulled from it yet) and `kotlinx-coroutines-play-services:1.7.3` for
  `Task<T>.await()` rather than hand-rolling a `suspendCancellableCoroutine`
  wrapper.
- Known gaps, deliberately left out as beyond the issue's acceptance
  criteria rather than silently swallowed: geofences do not survive device
  reboot (no `BOOT_COMPLETED` receiver added — the app-open resync covers
  it in practice for a family day-trip app opened regularly, but a
  reboot-then-never-reopened device would miss auto check-ins until next
  open); un-favoriting a place while standing inside its still-active
  notification does not proactively cancel that notification (no EXIT
  event fires for a geofence that's merely removed from registration, only
  for an actual physical exit).
- Tests: new `GeofenceNotificationSelectionTest` (7 cases covering
  `isCoolingDown`'s same/previous-day boundary and `closestEligibleFavorite`'s
  nearest-pick / cooldown-skip / all-cooling-down / empty-input cases) —
  pure JVM tests, no Robolectric, following the `CheckInRankingTest`/
  `isReadyForBanner` convention. Two new cases added to the existing
  `VisitDaoTest` for `lastVisitedAt`. `compileDebugKotlin`: clean.
  `testDebugUnitTest`: 133 total (was 124), 28 failed (was 26) — the +2 are
  the two new `VisitDaoTest` cases failing via the same pre-existing
  Robolectric `UnsatisfiedLinkError` (MapLibre native init) that already
  fails every other test in that class; confirmed via the XML report that
  no new failing test class was introduced.
- On-device pass with Robert caught a real bug the unit tests couldn't:
  `geofencePendingIntent` in `GeofenceSyncManager` was built with
  `FLAG_IMMUTABLE`, which crashed geofence registration at runtime with
  `ApiException: 10: PendingIntent must be mutable` — Play Services writes
  into that intent before redelivering it, so it can't be immutable (unlike
  the notification's own action `PendingIntent`s in `GeofenceNotifications`,
  which are correctly immutable since nothing external mutates those).
  Switched to `FLAG_MUTABLE`; confirmed the app now launches and registers
  geofences without crashing.
- Still not verified on device: actual ENTER/EXIT transitions firing (needs
  physically visiting/leaving a favorite, or a mock-location run), the
  multi-favorite "closest wins" behavior when two favorites are near each
  other, notification action buttons actually logging a `Visit` without
  opening the app, and the permission-revoked-mid-flight `SecurityException`
  path. Given the HITL flag on this issue, worth exercising these before
  merge rather than trusting the Play Services API surface read correctly.

## 2026-07-25 — Issue #27: Visit-frequency ranking boost for favorites

- Picked over #25/#26 (both unblocked, #23 closed): #25 is a docs-only decision
  amendment and #26 is a UI screen with no ranking impact, while #27 changes what

  applies the trailing-90-day window itself (via `context.nowMillis`) rather
  than trusting a caller-side cutoff. Mirrors how `verdicts`/`now` are already
  threaded through: the engine stays the single source of truth for what's
  "recent," consistent with its own "every rule is asserted by unit tests" doc
  comment.
- New score term in `evaluate()`: `VISIT_FREQUENCY_WEIGHT * ln(1.0 + recentVisits)`,
  `VISIT_FREQUENCY_WEIGHT = 10.0`. Chosen so a handful of visits (3 → ~13.9 pts)
  clearly outweighs the ~8-point novelty jitter and the few-point proximity gap
  between two nearby favorites, without swamping the distance-decay term (up to
  ~55 pts) that keeps "close by" the dominant signal. Also appends a reason
  string ("visited 3× recently") for card transparency, consistent with the
  other score terms.
- Wired `VisitDao` into `HomeViewModel`: added to the constructor + `Factory`,
  folded `visitDao.observeAll()` into the existing `poisVerdictsAndNames`
  `combine()` (still exactly 5 flows, the direct-overload limit) rather than
  adding a 6th flow to the outer `combine`, and grouped visits by `placeId` into
  `PoiSlice.visits` for `SuggestionContext`.
- Tests: new `SuggestionVisitFrequencyTest` (4 cases: no visits → no boost/no
  reason line; several recent visits → boost applied and outranks a same-slot
  favorite with none; visits outside the 90-day window → no contribution; a
  visit exactly at the 90-day boundary still counts). All existing
  `SuggestionContext(...)` call sites keep compiling unchanged since `visits`

## 2026-07-24 — Issue #23: Manual check-in for nearby POIs

- Picked over #24/#25/#27/#29 on purpose: this is the foundational slice —
  #26/#27 are directly blocked by it, and #28/#29 transitively depend on it —
  while #24 and #25 are unblocked but don't unblock anything else themselves.
- `Favorite` entity mentioned in the issue text no longer exists (dropped by
  `MIGRATION_3_4`, well before this session) — favoriting is a `Verdict` row
  with `value == Verdict.VALUE_FAVORITE` now. Read the DB layer before
  writing anything rather than trusting the issue's stale description.
- New `Visit` entity (`data/entity/Visit.kt`): auto-generated `id` (it's an
  append-only log, not a singleton row like `PendingVisit`) plus the same
  denormalized snapshot fields (`placeId`, `visitedAt`, `source`,
  `snapshotName/Lat/Lon/Category`) `Verdict`/`PendingVisit` already use, for
  the same reason — a visit must outlive the poi row it refers to.
