## 2026-09-10 — Issue #53: Widget empty/error states

- User-specified pickup (`/next-issue issue 53`). Confirmed `ready-for-agent` and unblocked (#51
  closed). Already fully resolved in the issue body per the epic's established convention; no
  `/grill-me` needed. Last open leaf of the widget epic besides #55 (twice-daily scheduled
  refresh, its own bigger/riskier slice per the #56 session's note).
- `SuggestionWidgetContent` gained a new pure `state()` function plus a `SuggestionWidgetState`
  sealed interface (`Rows`/`Hint`) and `HintDestination` enum (`EXPLORE`/`SETTINGS`) — mirrors
  HomeScreen's own `when` over `hasVerdictedPlaces`/`hasVerdictedPlacesWithinRadius` exactly (the
  `!hasPois` branch doesn't apply to the widget: an empty POI table also means no favorites, so it
  already falls out of `hasVerdictedPlaces`). `SuggestionWidget.provideGlance` now computes those
  same two booleans from the same `candidatePois`/`candidatesInRange` it already had (byte-for-byte
  the same expressions as `HomeViewModel.uiState`) and calls `state()` instead of `rows()`
  directly, so the widget and Home can never disagree about which of the three states applies.
- `SuggestionWidget.kt`: split the old single `SuggestionWidgetBody` into a shared
  `SuggestionWidgetScaffold` (background/padding/refresh-button row) plus two callers —
  `SuggestionWidgetBody` (normal rows, unchanged appearance) and a new `SuggestionWidgetHintBody`
  (one `Text` row, `maxLines = 2`, clickable, `onSurfaceVariant` styling to read as a hint rather
  than content) — so the two states fully replace each other rather than one showing alongside a
  partial/empty deck, per the issue's explicit note.
- The hint's tap target reuses the exact same `actionStartActivity(Intent(context,
  MainActivity::class.java)...)` shape #52 already built for per-row taps, just with a new
  `MainActivity.EXTRA_TARGET_DESTINATION` extra (a `FreizeitDestination.route` string) instead of
  `EXTRA_TARGET_POI_ID`. Wired that extra through `MainActivity` (new `targetDestination` state,
  read in both `onCreate` and `onNewIntent` alongside the existing `targetPoiId`) and `FreizeitApp`
  (new `targetDestination` param → `pendingTargetDestination`, consumed by a `LaunchedEffect` that
  calls a new `navigateToDestination()` local function — factored out of the bottom `NavigationBar`
  item's existing `onClick` lambda so a widget-driven tab switch takes the exact same
  `popUpTo`/`saveState`/`restoreState` path a manual tab tap does, rather than a second, subtly
  different nav call). "Explore" in the issue's wording maps to `FreizeitDestination.MAP` — the
  app has no screen literally named Explore; Map is where places actually get favorited/want-to-go'd,
  which is what's missing in that branch. New short strings (`widget_no_favorites_hint`,
  `widget_no_suggestions_within_radius_hint`) rather than reusing Home's own
  `home_no_favorites`/`home_no_suggestions_within_radius` — those are full paragraphs sized for
  Home's centered hint, not a compact widget row.
- Reverts to normal rows on its own (issue's third AC): no new code — `state()` is a pure function
  of the current data on every `provideGlance` call (widget add, manual refresh #54, or the
  event-driven trigger #56 already wired to every verdict/check-in/radius change), so a qualifying
  place existing again just makes the next call take the `Rows` branch instead of `Hint`.
- Tests: 260 total, 0 failures. New `SuggestionWidgetContentTest` cases for `state()`'s three
  branches (no verdicted places → `Hint(EXPLORE)`; verdicted places but none in radius →
  `Hint(SETTINGS)`; qualifying places → `Rows` matching plain `rows()`). No new test for
  `SuggestionWidget.kt`/`FreizeitApp.kt` themselves — same Glance/Compose-navigation
  Robolectric-free constraint prior widget-epic entries note; `navigateToDestination`'s reuse
  by both the bottom nav and the new effect is a one-line extraction, not judged worth a dedicated
  harness. `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`:
  all clean, no new warnings.
- Not verified on device: the actual tap — a hint row lands on Map/Settings respectively rather
  than Home, and the widget visibly reverts to normal rows on the next update once a qualifying
  place exists again — is real AppWidget-host/launcher + Activity-lifecycle behavior no unit test
  exercises, needs a real run on Robert's phone.

## 2026-09-10 — Issue #52: Wire widget row taps to the deep link

- User-specified pickup (`/next-issue issue 52`). Confirmed `ready-for-agent` and unblocked (#50
  and #51, its two blockers, both closed). Already fully resolved in the issue body per the
  epic's established convention; no `/grill-me` needed. This closes out the last of #52/#53/#55/
  #56's four leaves that was actually a hard blocker dependency (the other three were merely
  filed together); #53/#55/#56 remain open/closed independently per their own sessions.
- `SuggestionWidget.provideGlance` now builds one `actionStartActivity` per row instead of #51's
  single shared "open Home" action — each wraps an `Intent(context, MainActivity::class.java)`
  carrying that row's `SuggestionWidgetRow.poiId` via `MainActivity.EXTRA_TARGET_POI_ID` (the
  extra #50 already wired MainActivity/FreizeitApp/HomeViewModel.openTargetPoi to read and act
  on). `poiId` was already present on `SuggestionWidgetRow` from #51 — no `SuggestionWidgetContent`
  change needed, this issue is purely the tap-wiring #51's own note flagged as future work. Built
  in `provideGlance` (plain `Context`) rather than inline in the composable, same reason #51's
  single action was: `actionStartActivity`'s Intent-based vs. reified-generic overloads are
  ambiguous when called directly in a `@Composable` body. `SuggestionWidgetBody`/`SuggestionRow`
  now thread a `List<Pair<SuggestionWidgetRow, Action>>` instead of a bare row list plus one
  shared `Action`.
- Also set `FLAG_ACTIVITY_SINGLE_TOP` on each row's Intent, and reworded `MainActivity`'s
  `onNewIntent` doc comment (it already anticipated this exact case when #50 landed it). Without
  the flag, tapping a row while `MainActivity` was already running would launch a second instance
  via a fresh `onCreate` rather than deliver the new POI id to the existing one via `onNewIntent`
  — the issue's own "not on the (possibly already-reshuffled) deck" framing is specifically about
  the already-running case, so this felt like part of the same slice rather than a separate issue.
- Fallback for a vanished place (issue's third AC): no new code — `HomeViewModel.openTargetPoi`
  already resolves the id via `findPoiById` and fails quietly (`targetPoi` stays null, Home shows
  normally) if it doesn't resolve, per #50's own doc comment on that function. The widget doesn't
  need to know the difference between "still there" and "gone"; it just passes the id through.
- Tests: 257 total, 0 failures — no new tests, deliberately: same reasoning #51/#54 gave for
  `SuggestionWidget.kt` itself (Glance composables/`provideGlance` aren't unit-testable without
  Robolectric+the Glance test library, neither of which this repo has any pattern for). The one
  genuinely new piece of logic (per-row `Intent`/extra construction) is a two-line loop with
  nothing pure to extract — `SuggestionWidgetContentTest.kt` already covers `poiId` threading
  through `rows()`. `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/
  `assembleDebug`: all clean, no new warnings.
- Not verified on device: the actual tap — a row lands on that exact place's detail sheet, a
  second tap on a different row while the app is still open updates the same running instance via
  `onNewIntent` rather than opening a new one, and a row for a place deleted since the widget last
  rendered opens Home plainly instead of crashing — is real AppWidget-host/launcher +
  Activity-lifecycle behavior no unit test exercises, needs a real run on Robert's phone.

## 2026-09-10 — Issue #56: Event-driven refresh on verdict/check-in/radius changes

- Picked from four open `ready-for-agent` widget-epic issues (#52/#53/#55/#56): #54 (their shared
  blocker) closed since the last session, so all four are now unblocked leaves — none blocks any
  further filed issue, so the prior sessions' "unblocks the most downstream work" tiebreaker no
  longer discriminates between them. Picked #56 by actual user impact instead: without it, the
  widget only ever reflects reality at app-open/placement or a manual refresh tap (#54) — the most
  visibly-broken gap of the four, since favoriting a place or checking in and then glancing at the
  home screen would show stale content indefinitely. #52/#53 are rendering/interaction polish on
  content that's already there; #55 addresses the same staleness problem but only on a twice-daily
  clock, and is the bigger, riskier slice (introduces the app's first WorkManager/AlarmManager
  infrastructure) — better left its own pickup, same reasoning the #50 session used to defer #51.
  Already fully resolved in the issue body per the epic's established convention; no `/grill-me`
  needed.
- Implemented as one new reactive block in `FreizeitApplication.onCreate`, not as calls threaded
  through every ViewModel that can cause a qualifying change. Reused the file's own existing
  precedent one block up (issue #28/#29's geofence-sync `combine(...).collect { ... }`, which
  already reacts to `autoCheckInEnabled` + the favorites list rather than being invoked from each
  call site) — the same shape now also covers `verdictDao.observeAll()`,
  `visitDao.observeAll()`, and `settingsRepository.suggestionRadiusKm`. This one change transparently
  covers every current and future call site for the issue's three named triggers: both
  `HomeViewModel.setVerdict`/`MapViewModel.setVerdict`, all three ways a check-in gets recorded
  (`HomeViewModel.checkIn`, `CheckInViewModel.checkIn`, `GeofenceBroadcastReceiver`'s auto
  check-in — all write through the same `visitDao`), and `SettingsViewModel.setSuggestionRadiusKm`
  — without adding a widget-refresh dependency to four different ViewModels/receivers or risking a
  missed call site.
- Debounce (the issue's explicit AC) is `Flow.debounce(1_500ms)` on the combined trigger, same
  operator `CheckInViewModel`'s search box already uses (`SEARCH_DEBOUNCE_MS`) — just a longer
  window here since it's collapsing a few seconds of possible successive user actions (e.g.
  favoriting two places back to back) rather than keystrokes. A leading `.drop(1)` skips
  `combine`'s own immediate first emission of the three flows' startup values, so app launch itself
  never counts as a "change." `SuggestionWidgetUpdater.refreshAndPush` (#54) is already a no-op
  with no widget placed, so none of this costs anything (no location/weather fetch, no Room re-read
  beyond the observe queries Home already keeps live) when the widget isn't in use.
- Tests: 257 total, 0 failures — no new tests, deliberately: this is Application-level Flow
  orchestration glue with no pure logic of its own, mirroring why the geofence-sync block one

  `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean,

## 2026-09-10 — Issue #54: Manual refresh button + shared recompute routine

- Picked from five open `ready-for-agent` widget-epic issues (#52-#56): #55/#56 are blocked on
  this one (both explicitly "Blocked by #54"), while #52/#53 are unblocked leaves that unblock
  nothing further — #54 was the highest-impact pick by the same "unblocks the most downstream
  work" reasoning the #51 session used. Already fully resolved in the issue body per the epic's
  established convention; no `/grill-me` needed.
- New `ui/widget/SuggestionWidgetUpdater.kt`: the single shared "recompute and push" routine the
  issue asks for. It's deliberately thin — `SuggestionWidget().updateAll(context)` — rather than
  re-fetching location/weather itself, because [SuggestionWidget.provideGlance] (#51) already does
  the full fetch-rank-render sequence on every Glance re-render; calling it a second time here
  would just fetch location/weather twice per tap. `updateAll` re-invokes `provideGlance` for every
  placed instance, which *is* "fresh location fetch + weather refresh + recompute + re-render" —
  keeping that sequence defined in exactly one place (#51's file) rather than two. Note for
  whoever picks up #55/#56: call `SuggestionWidgetUpdater.refreshAndPush(context)`, don't
  reimplement the fetch-rank-render steps against the repositories directly.
- New `ui/widget/RefreshWidgetAction.kt`: a Glance `ActionCallback` (this repo's first — Glance
  instantiates it by class name via reflection, no manifest registration needed) that just calls
  the updater. Wired to a new refresh icon in `SuggestionWidget.kt`'s `SuggestionWidgetBody`: a
  20dp `Image` (new `res/drawable/ic_widget_refresh.xml`, a plain Material "refresh" glyph tinted
  via `ColorFilter.tint(GlanceTheme.colors.onSurfaceVariant)` so it follows the existing
  dynamic/fixed color split) in its own top-aligned `Row`, `clickable(actionRunCallback<
  RefreshWidgetAction>())` — a separate tap target from each `SuggestionRow`'s existing
  `openAppAction`, satisfying the issue's "distinct from the suggestion rows' tap targets".
  `actionRunCallback` (unlike #51's `actionStartActivity(Intent(...))`) has no Intent-based/
  reified-generic overload ambiguity, so it's called directly in the `@Composable` body rather than
  built in `provideGlance` first.
- Tests: 257 total, 0 failures — no new tests, deliberately: `SuggestionWidgetUpdater`/
  `RefreshWidgetAction` are Glance/Android glue with no pure logic of their own (same reasoning
  #51's `SuggestionWidget.kt` itself was left untested — Glance composables/`provideGlance`/
  `ActionCallback` aren't unit-testable without Robolectric+the Glance test library, neither of
  which this repo has any pattern for). `compileDebugKotlin`/`compileDebugUnitTestKotlin`/
  `testDebugUnitTest`/`assembleDebug`: all clean, no new warnings.
- Found (not fixed, out of scope): `ui/common/DurationBadge.kt` had an uncommitted, syntactically
  invalid edit sitting in the working tree at session start (`Color(/nex)` in place of a hex
  literal) that broke `kspDebugKotlin` for the whole module — visibly mid-edit in Robert's IDE per

## 2026-09-07 — Issue #49: Manual POI adding: reimport-time merge detection and confirmation

- Picked via `/next-issue issue 49` (user-specified). Confirmed `ready-for-agent` and unblocked
  (#45/#48 both closed). Already fully resolved in the issue body per the epic's established
  convention; no `/grill-me` needed. This is the last open issue in the "Manual POI adding" epic
  (#43) — #46/#47/#48/#49 are all now closed.
- New `util/NameSimilarity.kt` (pure, no existing helper to reuse per the exploration pass):
  normalizes (lowercase, collapse non-alnum runs to a single space) then matches on exact
  equality, substring containment either direction, or a normalized-Levenshtein similarity ratio
  above a threshold (0.6 default) — the "fuzzy substring/edit-distance" the issue asks for.
  New `util/CustomPoiMergeMatch.kt` layers this on top of the same distance+category shape as
  `CustomPoiProximity` (#45/#47) — reuses `GeoDistance`, same 40m threshold constant — but adds
  the name check `CustomPoiProximity` deliberately doesn't have (that one's a same-category-only
  dedup warning; #49 needs a real place-identity signal before ever proposing a merge). Yields at
  most one `MergeCandidate` per custom POI (its nearest qualifying match), so "no candidates"
  falls out naturally when nothing clears both thresholds.
- `PoiRepository.importFrom` now returns a new `ImportResult(count, mergeCandidates)` instead of
  a bare `Int` — candidates computed once the transaction commits, against `parsed.pois` (exactly
  what was just upserted) and a fresh `customPoiDao().getAll()`. New
  `PoiRepository.mergeCustomPoiInto(customPoiId, poiId)`: one `db.withTransaction` re-keying the
  Verdict (new `VerdictDao.rekey`, `UPDATE OR REPLACE` since `placeId` is that table's primary
  key — the rare case the target OSM place already had its own verdict is resolved in the custom
  POI's favor) and every Visit (new `VisitDao.rekey`, plain `UPDATE`, no PK conflict since `id` is
  the actual primary key there) onto the matched `poi.id`, then deletes the `custom_poi` row —
  deliberately the mirror image of `MapViewModel.commitPendingDelete` (#47), which deletes those
  rows outright instead of re-keying them; that method's doc comment already named #49 as the
  future contrast.
- `SettingsViewModel` gained a `mergeCandidates: StateFlow<List<MergeCandidate>>` (populated
  alongside `ImportStatus.Success` in `importPoiFile`) plus `confirmMerge`/`dismissMerge`, both of
  which pop the front entry — `SettingsScreen` renders only `mergeCandidates.firstOrNull()` as an
  `AlertDialog` (the existing two-button `confirmButton`/`dismissButton` shape already used for
  the auto-check-in disclosure dialog), so several candidates from one import walk through as a
  sequence of single dialogs rather than needing new stacked-dialog UI. Per the issue's explicit
  "no additional undo" — confirming just calls `mergeCustomPoiInto` and dismissing is a pure
  state-list edit, no Snackbar/undo path like #47's delete.
- Tests: 257 total, 0 failures. New `NameSimilarityTest.kt`, `CustomPoiMergeMatchTest.kt` (mirrors
  `CustomPoiProximityTest.kt`'s GeoDistance-derived-offset convention), `VerdictDao`/`VisitDao`
  `rekey` cases (including the already-has-a-verdict/visits-at-the-target-id edge cases), and
  `PoiImportTest.kt` additions covering `importFrom` surfacing (and not surfacing) candidates plus
  `mergeCustomPoiInto`'s full re-key-then-delete transaction end to end.
  `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean,
  no new warnings.
- Not verified on device: the actual Settings flow (import a `.pbf`-derived file that introduces a
  near-duplicate of an existing custom POI, confirm the dialog appears with the right two names,
  merge, and check the custom POI's marker/favorite/check-in history now live under the OSM
  place's id) is real Compose/Room integration no unit test exercises — needs a real
