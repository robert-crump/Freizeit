# Freizeit v2 progress log

## 2026-08-01 — Issue #40: update user location more frequently

- Issue was a stub (title + two-sentence body) — full design worked out via a `/grill-me` session
  before any code was touched (update model per screen, shared-vs-per-ViewModel location state,
  continuous-stream interval/priority, start/stop lifecycle scoping, manual refresh affordance,
  snapshot-vs-collect semantics for Home/Check-in, `GeofenceLocationMonitor` scope boundary —
  every branch resolved with the user first), posted to #40 as a comment, then implemented
  directly from that spec.
- Root cause: location was a plain one-shot `LocationManager.getLastKnownLocation()`
  (`util/LocationHelper.kt`), independently duplicated in `MapViewModel`/`HomeViewModel`/
  `CheckInViewModel` — no shared state, so the three screens could each show a different stale fix
  at the same moment; Map had no resume-based refresh at all.
- New `data/repository/LocationRepository.kt` (wired into `AppContainer` as a `by lazy` property,
  same pattern as `weatherRepository`/`geofenceStateRepository`): owns a
  `FusedLocationProviderClient` (already a dependency via `GeofenceLocationMonitor`), exposes a
  single `StateFlow<LatLon?>`. `refreshOnce()` is a one-shot `LocationHelper.lastKnownLocation()`
  read (unchanged semantics, just centralized); `startContinuous()`/`stopContinuous()` arm/disarm
  an active `LocationRequest` (`PRIORITY_BALANCED_POWER_ACCURACY`, 10s interval / 5s min),
  mirroring `GeofenceLocationMonitor`'s existing shape but left fully separate (different
  lifecycle/purpose — background significant-change re-ranking vs. foreground live tracking —
  explicit scope decision not to share the client instance).
- `MapViewModel`: its own `location: MutableStateFlow` is gone, `uiState`'s combine now reads
  `locationRepository.location` directly (continuous — Map is the one surface where a live
  position matters). New `startContinuousLocation()`/`stopContinuousLocation()` delegate straight
  to the repository. `MapScreen.kt`: new `DisposableEffect(lifecycleOwner)` calls
  `startContinuousLocation()`/`stopContinuousLocation()` on `ON_RESUME`/`ON_PAUSE` — since
  `MapViewModel` is hoisted at the `FreizeitApp` level and outlives tab switches, only the
  composable's own lifecycle knows when Map is actually the visible tab. Re-entering the Map tab
  replays `ON_RESUME` (`Lifecycle.addObserver` synchronously syncs a fresh observer up to the
  current state), which is also what fixes "switching to Map doesn't refresh location" — the same
  mechanism HomeScreen already used for its own resume refresh (#34). The existing "locate me"
  FAB's `refreshLocation()` call is untouched (already forced a fresh read; now goes through the
  repository).
- `HomeViewModel`/`CheckInViewModel`: `location` stays a local `MutableStateFlow`, but
  `refreshLocation()` now calls `locationRepository.refreshOnce()` then takes a one-time
  *snapshot* of `locationRepository.location.value` — deliberately not a continuous collection of
  the shared flow, so Map's background stream (or Check-in's new pull-to-refresh) can never
  reshuffle Home's swipe deck mid-session (#34's guarantee, explicitly re-verified during the
  grill-me session as the one real tension with #40's ask).
- `CheckInSearchScreen.kt` gains two things it never had before: a `DisposableEffect`/`ON_RESUME`
  observer identical to Home's (this screen previously only refreshed once via permission grant,
  so its distances/duration badges could be arbitrarily stale), and a Material3
  `PullToRefreshContainer`/`rememberPullToRefreshState()` wrapped around the results area (search
  results, favorites-nearby quick-picks, and the "no location" hint all share one `Box`) as a
  manual fallback — matches the user's established preference for always-available manual
  controls alongside automatic triggers. Confirmed the exact API shape against the project's
  resolved Material3 1.2.1 AAR directly (`PullToRefreshState.isRefreshing`/`startRefresh()`/
  `endRefresh()`/`nestedScrollConnection`, `PullToRefreshContainer`, `rememberPullToRefreshState()`
  — `PullToRefreshBox` doesn't exist until 1.3.0) before writing any code, same verify-before-
  relying-on-it approach as the date/time picker session's `DatePickerDialog`/`TimePicker` check.
  Since `refreshLocation()` is fire-and-forget (launches its own coroutine, doesn't suspend until
  done), the refresh indicator holds for a fixed 300ms (`PULL_TO_REFRESH_MIN_SPIN_MS`) rather than
  truly awaiting completion — pragmatic given a last-known-location read is near-instant anyway,
  avoids adding a second suspend-returning API just for this.
- `MapViewModel`/`HomeViewModel`/`CheckInViewModel` constructors: `appContext: Context` param
  replaced by `locationRepository: LocationRepository` in all three (each `Factory` updated to
  pass `app.container.locationRepository`); `LocationHelper` import dropped from all three
  ViewModels (still used as-is by `MapScreen.kt`/`CheckInSearchScreen.kt` for the unrelated
  permission-check flow, untouched).
- Tests: 160 total, 0 failures (unchanged — no test file needed changes; this issue's scope is
  pure ViewModel/Compose wiring around already-tested pure functions, none of which changed
  signature). `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/
  `assembleDebug`: all clean, no new warnings (the two pre-existing ones —
  `CheckInViewModel.kt`'s `FlowPreview` opt-in and `PoiMap.kt`'s unused `customNames` param — are
  both unchanged from before this session).
- Not verified on device: the entire continuous-stream/lifecycle wiring (Map's GPS stream actually
  starting/stopping on tab switch and app background/foreground, the "locate me" FAB still
  recentering correctly, Check-in's new resume refresh and pull-to-refresh indicator, and Home's
  deck genuinely not reshuffling mid-swipe even while Map is streaming in the background) is new
  platform/Compose wiring with no prior on-device confirmation — needs a real run on Robert's
  phone, particularly battery behavior over a longer Map session and confirming the pull-to-
  refresh gesture doesn't fight the search screen's own scrolling.

## 2026-07-31 — Check-in date/time picker

- No GitHub issue; user asked directly for this, worked out via a full /grill-me session before
  any code was touched (scope across both entry points, dialog flow shape, picker widget style,
  final-confirm vs immediate-create, undo affordance, future/past bounds, time-of-day enforcement,
  notification flow, cancel semantics, `checkIn()` API shape, code reuse — every branch resolved
  with the user first).
- Both Check-in entry points (Home's suggestion-card button and the Check-In screen's row tap)
  used to open an identical `AlertDialog` ("Do you want to check into X?") that, on confirm,
  stamped `visitedAt = System.currentTimeMillis()` immediately. Replaced with a two-step flow,
  explicitly *not* keeping that confirm-text step: tapping Check-in goes straight to a Material3
  `DatePickerDialog` (defaulted to today, `SelectableDates` disables future days), confirming opens
  a time picker (defaulted to now, dial + keyboard-input toggle), and confirming that creates the
  check-in immediately — no third "are you sure" step. Cancelling either dialog aborts the whole
  attempt (explicit decision: cancelling the time step does *not* fall back to the date step).
  Time-of-day itself is deliberately left unenforced even when the picked date is today (only the
  day itself is capped at "no future") — Material3's `TimePicker` has no way to disable specific
  times, and the user chose not to hand-roll validation for it.
- New shared `ui/checkin/CheckInDateTimeFlow.kt`, used by both `HomeScreen.kt` and
  `CheckInScreen.kt` (their old dialogs were already byte-for-byte duplicated; explicit decision to
  consolidate into one composable now rather than duplicate the picker flow too).
  `CheckInDateTimeFlow` takes `pendingPoi: Poi?` and is called unconditionally every recomposition
  (not wrapped in a null check) specifically so its `rememberCoroutineScope()` — used to launch the
  confirm→save→snackbar→undo chain — stays alive across a cancelled/restarted attempt; the
  per-attempt picker state (`pickedDateMillis`, dial/keyboard toggle) still resets correctly because
  those `remember` calls sit after an early `return` that's skipped whenever `pendingPoi` is null,
  so Compose tears down and recreates that part of the slot table each time. Material3 1.2.1 (this
  project's resolved `compose-bom:2024.02.02` version, confirmed by inspecting the AAR directly)
  ships `DatePickerDialog` but no dialog wrapper for `TimePicker`/`TimeInput` — added a small
  hand-rolled `CheckInTimePickerDialog` (plain `Dialog` + `Surface` + title/content/buttons row),

- `VisitDao.checkIn()` gained an optional `visitedAt: Long = System.currentTimeMillis()` param

  `HomeViewModel.checkIn`/`CheckInViewModel.checkIn` changed from fire-and-forget
  `viewModelScope.launch` functions to `suspend fun checkIn(poi, visitedAt): Long`, called directly
  from `CheckInDateTimeFlow`'s own coroutine scope (not the ViewModel's) — deliberate, so the
  confirm→save→snackbar→undo sequence is one linear suspend chain instead of state bounced through

  undoCheckIn(visitId)` (`visitDao.deleteByIds(listOf(visitId))`).
- Snackbar + Undo (explicit decision, matching the existing delete-undo pattern in

## 2026-07-30 — Issue #19: swipe-deck flicker fix

- Not picked from the tracker cold — diagnosed live with the user via `/grill-me` against a
  specific repro (swiping Home's suggestion deck one direction briefly flashes a stale, unrelated
  card before landing on the correct one; the other direction never does), then implemented that
  fix. Addresses only issue #19's third bullet ("Flicker is still there when swiping through card
  deck"); its other two bullets (remove fading animation, wrap_content sizing) are untouched and
  out of scope for this session — closed anyway per the user's explicit instruction after
  confirming the flicker fix on device; re-file the other two separately if still wanted.
- Root cause, confirmed with the user before touching code: `SwipeableSuggestionCard`
  (`HomeScreen.kt`)'s window is always emitted in a fixed `[previousCard, nextCard, card]` order,
  and later Box children paint on top of earlier ones — deliberately, so `nextCard`'s idle peek
  sliver (not `previousCard`'s identical one) is what shows as the deck's "stackable" affordance
  at rest. But that static order held during an active drag too: revealing `previousCard` grows
  it past `nextCard`'s small idle-peek footprint, and since `nextCard` is emitted after (so always
  painted above) `previousCard`, `nextCard`'s idle sliver stayed visible on top of the growing
  card for the whole reveal — reads as a wrong-card flash that self-corrects once the drag commits
  and the window recomputes. Only affects revealing `previousCard`, matching the reported
  direction asymmetry: revealing `nextCard` never has this problem since the idle card
  (`previousCard`) is the one underneath in that case.
- Fix: added `isRevealTarget`/`revealZIndex` (pure, alongside the existing
  `topCardAlpha`/`revealProgress`/`isPastSwipeThreshold`) and wired `Modifier.zIndex()` into both
  branches of the per-entry modifier — current always highest, then whichever neighbor the drag is
