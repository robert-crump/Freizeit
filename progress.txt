## 2026-09-07 — Issue #46: Manual POI adding: address search for custom POI creation

- User explicitly picked this one (`/next-issue issue 46`) rather than the usual "pick the
  highest-impact open issue" — skipped the epic-priority writeup other recent entries include.
  Confirmed `ready-for-agent` and unblocked (#45 closed); already fully resolved in the issue body
  per the epic's established convention, no `/grill-me` needed.
- New `data/geocoding/NominatimClient.kt` (object, mirrors `OpenMeteoClient`'s exact pattern: plain
  `HttpURLConnection` + Gson, one GET per search, null-on-any-failure) plus a new
  `domain/geocoding/GeocodeResult.kt` (lat/lon/displayName/street/housenumber/postcode/city — the
  reduced shape the rest of the app needs, not Nominatim's full response). `search()` biases (not
  restricts — `bounded=0`) to the same Aachen/South Limburg box as
  `tools/poi_extraction/extract_pois.py`'s `AACHEN_BBOX`, duplicated as a literal since one side is
  Python. User-Agent identifies the app + repo URL rather than a personal contact address — real
  per Nominatim's usage policy (a default HttpURLConnection one is rejected) without sending any
  user-identifying data to this third-party service.
- UI lives in `AddPoiPinOverlay` (the pin-drop step), not the form: a new `AddressSearchBar`
  private composable — `OutlinedTextField` + explicit "Search" button/IME action (no live-
  typeahead, respects Nominatim's 1 req/sec policy without debounce logic), permanent "©
  OpenStreetMap contributors" caption beneath it, and a results `Card` below that. Selecting a
  result re-centers the pin by reusing the existing `MapViewModel.focusOn` camera-jump path (its
  resulting camera-idle callback already feeds `updateAddPoiCenter` during `PLACING_PIN`) rather
  than inventing a second "move the crosshair" mechanism, and stashes the structured address in a
  new `pendingAddressPrefill` StateFlow. `AddPoiForm` gained a `prefillAddress: GeocodeResult?`
  param seeding street/housenumber/postcode/city (still editable after) whenever `initial` (#47's
  edit flow) is null — edit's own values always win since it never re-enters pin-placement/search.
- `MapViewModel` gained `AddressSearchState` (query/results/isSearching/error/searched — `error`
  vs. an empty `results` list are distinct so the empty-state message only shows after a genuine
  zero-match search, not a network failure) plus `updateAddressSearchQuery`/`searchAddress`/
  `selectAddressResult`. `searchAddress`'s IO-dispatched response checks the query hasn't changed
  since the request fired before applying it (mirrors `selectPoi`'s existing late-response guard)
  rather than adding a generation counter. Both new StateFlows are cleared in `cancelAddPoi` and
  `saveCustomPoi` alongside the existing `addPoiCenter`/`editingCustomPoi` resets.
- Tests: 228 total, 0 failures. New `NominatimClientTest.kt` (mirrors `OpenMeteoClientTest`'s
  pattern): result-array parsing into `GeocodeResult`s, city→town→village fallback, empty array vs.
  null-on-garbage/non-array JSON, a hit missing lat/lon dropped rather than crashing the whole
  parse, and blank-query search short-circuiting before any network call. No Compose-level test for
  the prefill precedence (`initial` over `prefillAddress`) or the search bar itself — same
  Robolectric-free constraint noted in prior entries for this file's other Compose pieces;
  the underlying logic is a one-line `?:` chain, not judged worth a dedicated harness.
  `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean,
  no new warnings.
- Not verified on device: an actual Nominatim round trip (rate-limit behavior, real result
  ordering/quality for Aachen/South Limburg addresses, a genuine network-failure inline message)
  and the visual layout of the new search bar/results card sitting above the pin crosshair — needs
  a real run on Robert's phone.

## 2026-09-07 — Issue #51: Minimal Glance widget: top-3 suggestions

- Picked from eight open `ready-for-agent` issues: of the three actually unblocked (#46/#49, the
  remaining Manual POI adding leftovers; #51 itself), #51 was the highest-impact pick by a wide
  margin — it's the foundation five other filed issues (#52-#56) all transitively depend on,
  versus #46/#49 which unblock nothing further. The prior #50 session had explicitly deferred
  #51 for exactly this reason ("a much bigger single slice better left as its own pickup") —
  picking it up now as that dedicated pickup. Already fully resolved in the issue body per the
  epic's established convention; no `/grill-me` needed.
- New `androidx.glance:glance-appwidget:1.1.1` + `androidx.glance:glance-material3:1.1.1`
  dependencies (`app/build.gradle`) — the app's first Glance usage, no prior widget
  infrastructure to extend. `SuggestionWidgetReceiver`/`SuggestionWidget` in a new `ui/widget`
  package, registered in `AndroidManifest.xml` + new `res/xml/suggestion_widget_info.xml`
  (2x1 min, resizable up to 5-rows-tall, `previewImage`/`description` for the widget picker).
  Deliberately no `updatePeriodMillis` — #55 is explicitly filed as "the app's first periodic
  background job," so this slice doesn't jump ahead and add scheduling of its own.
- No new ranking logic, per the issue's own spec: `SuggestionWidget.provideGlance` mirrors
  `HomeViewModel`'s exact data assembly (same `poiDao.observeByVerdictValues` candidate pool,
  `verdictDao`/`visitDao`/`poiCustomNameDao` one-shot reads via `.first()`/`getAll()` instead of
  `combine`, `locationRepository.refreshOnce()` + `weatherRepository.refresh()`, then
  `SuggestionEngine.withinRadius` → `rankAll`) rather than reusing `HomeViewModel` itself (a
  `ViewModel` isn't something a `GlanceAppWidget` can hold — no `ViewModelStore` to own it).
  Note for whoever picks up #52/#53: Home's own candidate pool is `poiDao.observeByVerdictValues`
  only, never merged with `customPoiDao` the way `MapViewModel`/`CheckInViewModel` are (#48) — a
  favorited *custom* POI currently won't appear in Home's deck *or* this widget. Mirrored
  faithfully rather than silently fixed here (out of scope for #51's "no new ranking logic"), but
  worth its own issue if confirmed on Robert's phone.
- Row content (`SuggestionWidgetContent.kt`, new, pure/no Android types): `rows()` resolves each
  suggestion's display name (`customNames` override → `poi.name` → an "Unnamed <category>"
  fallback, mirroring `Poi.displayName()`'s precedence but as a plain function since that one's
  `@Composable`-only) and travel-time label, both via caller-supplied formatter lambdas so the
  actual `context.getString(R.string.map_unnamed/duration_minutes, ...)` calls happen once in
  `SuggestionWidget` and this file stays unit-testable with no Robolectric. `rowCountForSize()`
  and the `WIDGET_SIZES` breakpoint list (Android's `70dp*cells-16dp` cell-size formula, 1..5
  rows) are the single source both `SizeMode.Responsive`'s declared sizes and the row-count
  lookup read from, so they can't disagree about what a given placed size means.
- Theming: below Android 12, `SuggestionWidgetColors` wraps `FreizeitTheme`'s own
  `LightColors`/`DarkColors` (now `internal` rather than `private` in `Theme.kt` specifically so
  this file can reuse them instead of re-deriving the same four color values) in
  `androidx.glance.material3.ColorProviders`; Android 12+ uses `GlanceTheme.colors`'s own dynamic
  wallpaper-derived scheme untouched.
- Tap target: generic `actionStartActivity(Intent(context, MainActivity::class.java))`, built
  once in `provideGlance` (plain `Context`, not inside the `@Composable` body) specifically to
  dodge an overload-resolution ambiguity between `actionStartActivity`'s Intent-based and
  reified-generic-type signatures that `compileDebugKotlin` caught immediately when tried inline.
  #52 swaps this for a per-row `PendingIntent` carrying the tapped place's id.
- Tests: 222 total (fresh `clean` run — the "351" prior sessions kept citing was and remains
  stale/wrong, per #47's session note; not re-investigated, still out of scope for this issue),
  0 failures. New `SuggestionWidgetContentTest.kt` (row capping/ordering, travel-label
  formatting incl. the null-travel-minutes case, custom-name precedence, `rowCountForSize`
  boundary behavior, `WIDGET_SIZES` internal consistency). No test for `SuggestionWidget` itself
  — Glance composables/`provideGlance` aren't unit-testable without Robolectric+the Glance test
  library, neither of which this repo has any existing pattern for; all the actual logic worth
  asserting was already pulled into the pure `SuggestionWidgetContent` above.
  `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`: all
  clean, no new warnings (same pre-existing `LocalLifecycleOwner`/unused-`customNames` warnings
  as before).
- Not verified on device: the entire actual widget experience — adding it from the picker,

## 2026-09-07 — Issue #50: Deep-link Home to a specific place's detail sheet

- Picked from the widget epic (design discussion referenced by #51-#56): of the two entirely
  unblocked issues (#50, #51) plus the two remaining Manual POI adding leftovers (#46, #49, both
  ready since #45/#48 closed), #50 was the highest-impact pick — it's foundational plumbing that
  #52 depends on, has no new Gradle dependency to introduce (unlike #51's Glance widget, a much
  bigger single slice better left as its own pickup), and is fully self-contained/independently
  testable per the issue's own spec. Already fully resolved in the issue body per the epic's
  established convention; no `/grill-me` needed.
- `MainActivity` gained a `mutableStateOf<String?>` `targetPoiId`, read from a new
  `EXTRA_TARGET_POI_ID` intent extra in `onCreate` and re-read in a new `onNewIntent` override
  (calls `setIntent` first) — a `mutableStateOf` rather than a plain `var` specifically so a
  relaunch delivered to an already-running Activity (e.g. a future widget tap using
  `FLAG_ACTIVITY_SINGLE_TOP`) recomposes `FreizeitApp` with the new value instead of only ever
  taking effect on a cold start.
- `FreizeitApp` takes the new `targetPoiId` param and holds it in `pendingTargetPoiId`
  (`rememberSaveable(targetPoiId)`, so it resets whenever a *new* incoming value arrives but
  otherwise survives ordinary recompositions), passed to `HomeScreen` alongside an
  `onTargetPoiIdHandled` callback that clears it back to null — this is what stops the sheet from
  reopening on a later tab revisit, since `HomeScreen`'s own composable lambda re-executes fresh
  each time Home re-enters the NavHost.
- `HomeScreen` resolves the id via a new `LaunchedEffect(targetPoiId)` (fires once per distinct
  non-null value, satisfying the issue's "once, not on every recomposition/resume") calling
  `HomeViewModel.openTargetPoi`, then immediately invokes `onTargetPoiIdHandled`. The sheet itself
  reuses `PlaceDetailSheet` as-is (its own doc comment already claimed "opened from map markers,
  list rows, and Home cards" — Home didn't actually do this yet before this session; now it does)
  rather than building a second detail view.
- `HomeViewModel.openTargetPoi` mirrors `MapViewModel.selectPoi`'s pattern: resolves the id via
  the existing `findPoiById` (#48's `PoiLookup.kt`, already covers both `poi`/`custom_poi` tables
  and is already unit-tested), computes distance against the current cached location via
  `GeoDistance.metersBetween` (already unit-tested), and looks up `lastVisitLabel`. An id that
  doesn't resolve (deleted place, stale/bad extra) just returns early — `targetPoi` stays null and
  Home renders normally, no crash, per the issue's explicit acceptance criterion. `HomeViewModel`
  also gained a `setCustomName` (mirroring `MapViewModel`'s) since `PlaceDetailSheet` requires a
  non-null `onCustomNameChange` callback — `HomeViewModel`'s existing `poiCustomNameDao` and a new
  `customPoiDao` constructor dependency (added to `HomeViewModel.Factory`, same
  `app.container.database.customPoiDao()` source `MapViewModel.Factory` already uses) make this
  possible with no new DB access needed.
- Tests: 217 total, 0 failures — no new tests, deliberately: this issue is orchestration/wiring
  over primitives that are already unit-tested (`findPoiById`/`PoiLookupTest.kt`,
  `GeoDistance.metersBetween`/`GeoDistanceTest.kt`), the same reasoning `MapViewModel.selectPoi`
  (which this mirrors) was never itself given a dedicated test either.
  `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/`assembleDebug`: all clean,
  no new warnings.
- Not verified on device: the actual deep-link launch (`adb shell am start -n
  com.example.freizeit/.ui.MainActivity --es target_poi_id <id>`) is real Activity-intent/Compose
  lifecycle behavior no unit test exercises — needs a real run on Robert's phone per the issue's
  own verification method, confirming the sheet actually auto-opens on a cold launch, an
  already-unresolvable id falls back cleanly, and (once #52 exists) a widget row tap resolves the
  same way.

## 2026-09-07 — Issue #47: Manual POI adding: edit/delete custom POI, with undo

- Picked from the "Manual POI adding" epic (#43): of the three remaining open issues (#46/#47/#49,
  all unblocked now that #45/#48 are closed), #47 was the highest-impact pick — it's the only one
  of the three fixing a real gap in already-shipped functionality (a custom POI, once created, has
  no way to fix a typo or remove one added by mistake) rather than adding a new capability on top
  (#46's address search, #49's reimport merge-detection). Also the best fit for the user's own
  stated preference for undo/safety-net affordances on destructive actions (see
  `feedback-ux-safety-nets.md`). Already fully resolved in the issue body per the epic's
  established convention; no `/grill-me` needed.
- Edit and Delete actions added to `PlaceDetailSheet` (`onEdit`/`onDelete`, both nullable — omitted
  entirely, not shown disabled, for an OSM-sourced `Poi`); `MapScreen` only ever passes non-null
  callbacks when `isCustomPoiId(item.poi.id)`.
- Edit reopens `AddPoiForm` pre-filled via new `Poi.toCustomPoi()` (`CustomPoi.kt`) — the exact
  reverse of the existing `toPoi()` projection, round-trip-tested in `CustomPoiTest.kt` — skipping
  pin-placement entirely (the location itself isn't editable here, only the form fields) and
  saving through the existing `id` rather than minting a new one. `AddPoiForm` gained an `initial:
  CustomPoi? = null` param seeding every field; the id-preservation logic itself was pulled out
  into a new pure `buildCustomPoiCandidate()` (mirroring this file's own convention of extracting
  pure logic for testability) and unit-tested directly (`BuildCustomPoiCandidateTest.kt`) rather
  than only through Compose. `CustomPoiProximity.findNearbyMatch` gained an `excludeId` param so
  editing in place (same lat/lon, unchanged) doesn't trip its own "already exists" warning against
  itself — regression-tested in `CustomPoiProximityTest.kt`.
- Delete is optimistic per the issue's spec: `MapViewModel.requestDeleteCustomPoi` sets a new
  `pendingDeleteCustomPoiId` and closes the sheet; `poisVerdictsAndNames`' merge now runs a new
  pure `excludePendingDelete()` (unit-tested in `PendingCustomPoiDeleteTest.kt`) so the marker
  disappears from the map/search instantly while the `custom_poi`/`Verdict`/`Visit` rows are
  untouched in the DB. Since nothing is actually deleted yet, `undoDeleteCustomPoi()` is just
  clearing that pending id back to null — "restoring" the Visit/Verdict needs no extra work because
  they were never removed. `MapScreen` shows a "Deleted — Undo" Snackbar (own `SnackbarHostState`,
  same `showSnackbar`+`SnackbarResult` pattern as `CheckInDateTimeFlow`'s check-in undo): Undo taps
  call `undoDeleteCustomPoi()`, a timeout/swipe-dismiss calls `commitPendingDelete()` (which deletes
  the Verdict, every Visit via new `VisitDao.deleteByPlaceId()`, then the `custom_poi` row itself,
  in that order). A `DisposableEffect(Unit)` in `MapScreen` also calls `commitPendingDelete()` on
  dispose, covering the spec's "or the user navigates away" case if the Snackbar never resolves on
  its own (e.g. switching bottom-nav tabs mid-countdown) — safe to call unconditionally since it
  no-ops once nothing is pending.
- Tests: 217 total (this repo's actual current count — noting it since the last two progress
  entries' claimed "351" doesn't match either `@Test` grep or the JUnit XML output, seemingly a
  stale/incorrect figure carried forward; not investigated further as out of scope for #47), 0
  failures. New: `BuildCustomPoiCandidateTest.kt`, `PendingCustomPoiDeleteTest.kt`, two
  `CustomPoiTest.kt` cases (`toCustomPoi` round trip + null-name fallback), two
  `CustomPoiProximityTest.kt` cases (`excludeId`), two `VisitDaoTest.kt` cases
  (`deleteByPlaceId`). `compileDebugKotlin`/`compileDebugUnitTestKotlin`/`testDebugUnitTest`/
  `assembleDebug`: all clean, no new warnings.
- Not verified on device: the Snackbar timing/Undo tap and the DisposableEffect's navigate-away
  commit are real Compose lifecycle/timing behavior no unit test exercises — needs a real
  edit-a-custom-POI and delete-then-undo-then-let-it-time-out pass on Robert's phone, plus
  confirming a deleted custom POI's marker, favorite/verdict, and check-in history are all
  actually gone after the Snackbar times out (not just visually hidden).

## 2026-09-07 — Add-POI header alignment + Google Maps-style compass

- No GitHub issue; user asked directly for two Map-screen fixes noticed while using the add-POI
  flow (#45). Implemented directly, no `/grill-me` needed — both were concrete, unambiguous asks.
- Add-POI header alignment: `AddPoiPinOverlay`'s back-arrow/hint row and `AddPoiForm`'s back-
  arrow/title row both called `.statusBarsPadding()` on top of an already-applied top inset —
  `MapScreen` (and by extension anything it hosts, including these two full-screen steps) already
  sits inside `FreizeitApp`'s `Scaffold`-provided `innerPadding`, which accounts for the status bar
  itself. The doubled inset pushed both rows visibly below `SearchOval`, which relies on that same
  single inset and adds no `statusBarsPadding` of its own. Fix: dropped `.statusBarsPadding()` from
  both and matched their `Row` padding to `horizontal = 4.dp, vertical = 8.dp` (already what
  `AddPoiForm`'s row used) — now both align with `SearchOval`'s top position and with each other.
- Compass: MapLibre's compass was never actually broken (fade-facing-north — hidden at north,
  fades in on rotation, tap resets to north — is already the SDK default and left otherwise
  untouched, just made explicit via `setCompassFadeFacingNorth(true)`); it was rendering at its
  default top-right position *underneath* `MapScreen`'s Compose `SearchOval`+`PoiCategoryChipRow`
  column, which is drawn on top of the native `MapView` in the same `Box` and spans the full width
  of that same top strip — permanently invisible regardless of bearing. Fix: `MapScreen` measures
  that column's actual rendered height via `Modifier.onGloballyPositioned` (not a fixed dp guess —
  stays correct if the category row is ever empty, or system font scale changes its height) and
  passes it down as `PoiMap`'s new `compassTopMarginPx`, which nudges only the compass's top
  margin (via `UiSettings.setCompassMargins`, left/right/bottom untouched) to clear that column
  plus an 8dp gap. Zeroed out during the add-POI pin-placement step, where that column isn't shown.
- Tests: 351 total, 0 failures (unchanged — no pure function touched; both fixes are Compose
  layout/native-widget wiring). `compileDebugKotlin`/`compileDebugUnitTestKotlin`/
  `testDebugUnitTest`/`assembleDebug`: all clean, no new warnings.
- Not verified on device: both are visual fixes with no unit-test coverage possible — needs a real
  run on Robert's phone, particularly the compass's fade timing/position relative to the category
  chip row (including with zero categories, where that row still reserves ~16dp), and rotating the
  map to confirm it fades in and tapping it resets to north.
